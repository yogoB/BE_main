# 데이터 운영·개인화·수익 모델 검토

2026-09-15 사용자 요청에 따른 검토안. 현재 구현과 제안을 구분한다.
새 API 계약·개인화 저장 모델·과금 정책을 확정한 문서는 아니다.

## 1. 우체국 장애와 CSV 갱신

**추천: DB의 마지막 정상 데이터를 계속 제공하고, 검증한 CSV를 갱신 소스로 함께 운영한다.**
API 장애가 발생할 때마다 과거 CSV를 재적재하면 최신 가격이 과거 가격으로 돌아갈 수 있다.
CSV는 초기 복원용 자료이면서 사람이 확인한 변경사항을 공급하는 경로로 둔다.

### 현재 있는 것

- `CatalogSeedLoader.loadMobilePlans`: PostgreSQL COPY → 임시 테이블 → 통신사/요금제 업서트.
  `(carrier_id, name)` 기준으로 ID를 유지하며 잘못된 행은 전체 트랜잭션을 롤백한다.
- 시작 시 classpath의 `db/seed/mobile_plan.csv`가 있으면 적재한다. 실행 중 파일 갱신을 자동 반영하는 기능은 없다.
- `MvnoCatalogLoader`: 하루 1회 API 결과를 같은 `mobile_plan`에 업서트한다.
  키 미설정·호출 실패 시 기존 DB 유지. 현재 로컬 우체국 키는 미설정이다.
- 두 로더 모두 수집일이 더 오래된 입력인지 확인하는 충돌 방지가 없다. API는 행별 반영이어서 부분 성공이 가능하다.

### 최소 구현안

1. 원본 CSV는 날짜별로 보관하고, 서비스 입력은 기존 템플릿으로 정규화한다.
   금액·MB·무제한 표기·공식 출처·확인일을 검수한다. 파일에 있다는 이유만으로 `OFFICIAL`로 승격하지 않는다.
2. 기존 COPY/스테이징 로더를 재사용한다. 운영자가 지정한 외부 파일 경로를 읽는 내부 갱신 경로를 추가하면
   JAR 재빌드 없이 교체할 수 있다. 공개 CSV 업로드 API나 별도 수집 서버는 필요 없다.
3. 모든 행 검증 후 한 트랜잭션으로 반영한다. 오류·빈 결과·API 장애는 DB 삭제 조건이 아니다.
   CSV 파일도 임시 파일 작성 후 이름 교체로 배포해 절반만 작성된 파일을 읽지 않게 한다.
4. 오래된 확인일의 입력은 새 값을 덮어쓰지 못하게 한다. 확인일이 같고 값이 다르면 자동 변경을 보류하고
   차이를 기록한다. 현재 `collected_at`은 DATE라 같은 날의 선후를 판정할 수 없다.
   더 정밀한 자동 병합이 필요해질 때 출처의 기준시각과 실제 수집시각을 분리한다.
5. API가 복구되면 같은 검증·신선도 규칙으로 갱신한다. CSV에서 사라졌다는 이유만으로 상품을 삭제하지 않는다.
   판매 종료는 별도 공식 확인이 필요하며, 회원이 참조하는 요금제 ID도 유지해야 한다.

초기 실행 방식은 운영자 명시 실행 또는 재기동 적재로 시작하고, 파일 운영 절차가 정해지면 하루 1회 예약한다.
최근 정상 확인일을 보존하며 장애 시각을 `collected_at`으로 덮어쓰지 않는다.
화면의 오래된 자료 안내·판매 종료 표시가 필요하면 사람 관리 API 계약에 함께 제안한다.

구현 완료 판정: **API 키 없이 초기 복원 / 새 CSV 갱신 / 과거 CSV 역행 차단 / 무효 행 전체 롤백 /
API 실패 시 DB 불변 / 재실행 시 중복 없음 / 참조 중인 요금제 ID 유지.**
이번 검토에서 이 갱신 기능을 구현 완료했다고 보지 않는다. 다음 백엔드 구현의 우선순위 1이다.

## 2. 스마트초이스 실연동 검증 상태

**아직 실데이터 수집 성공으로 판정할 수 없다.**

| 확인 단계 | 2026-09-15 결과 |
|---|---|
| 로컬 모의 HTTP 응답의 파싱·오류 처리 | 테스트 존재·통과 |
| 모의 응답 → PostgreSQL 스냅샷 업서트·중복 방지 | 테스트 존재·통과 |
| 기존 시드와 시세 대조, 계산 결과 불변 | 테스트 존재·통과 |
| 로컬 `SMARTCHOICE_API_KEY` 설정 | 값 존재 확인. 승인·유효성을 뜻하지 않음 |
| `https://api.smartchoice.or.kr/openAPI.xml` 실요청 | HTTP 404 |
| `https://api.smartchoice.or.kr/api/openAPI.xml` 실요청 | HTTP 200, `result_code=001`, `result_count=0`, 요금제 필드 없음 |
| 실제 요금제 응답 파싱·DB 적재·추천 교차검증 | 미검증 |

HTTPS 요청은 키를 출력·저장하지 않고 응답 상태와 제한된 필드만 기록했다. 운영 DB에는 쓰지 않았다.
스마트초이스 [공식 API 안내](https://m.smartchoice.or.kr/smc/openapi/openapiguide_02.do)의 검색 색인은
`001`을 인증키 없음으로 설명한다. 등록한 키가 요청에서 왜 인정되지 않았는지는 이 결과만으로 확정할 수 없다.
현재 공식 안내 페이지 본문은 조회 시 타임아웃이었다.

실수신 XML은 `root/result_code/result_date/result_count`였고 현재 클라이언트의 성공 판별은
`resultCode`를 전제로 한다. **주소와 응답 형식 모두 실제 성공 응답을 확보해 대조해야 한다.**
기본 클라이언트 주소는 HTTP다. HTTPS 지원 주소·등록키·요청 방식 확인 전 키를 평문 HTTP로 보내는 운영을 확정하지 않는다.
이번 HTTPS 검사 결과를 현재 HTTP 기본 주소의 실행 성공/실패와 혼동하지 않는다.

다음 순서:

1. 발급 화면의 활성 키·허용 서비스·등록 IP 조건과 공급자가 안내한 정확한 주소/파라미터를 확인한다.
2. 승인된 환경에서 1회 조회로 성공 코드와 실제 요금제 1건 이상을 확보한다.
3. 키 없는 응답 샘플을 테스트 fixture로 남겨 파서의 태그·가격·망·단위 가정을 수정한다.
4. 단건을 검증 DB에 저장하고 통신사·요금제명·정상가를 공식 자료와 대조한다.
5. 그 후 54회 스윕과 재실행 중복 방지, `priceCrossCheck` 노출을 확인한다.

스마트초이스는 사용조건당 추천을 반환하므로 전체 카탈로그 확보를 보장하지 않는다.
지금처럼 별도 시세 대조용으로 두고, 주 카탈로그는 우체국/검수 CSV로 확보하는 것이 적합하다.

## 3. 개인화된 사용자 관리

**추천 형태: 비회원의 일회성 비교 + 회원의 지속적인 내 지출 관리.**
Google·자체 로그인 모두 같은 내부 userId의 데이터를 사용한다.

| 화면/행동 | 현재 활용할 구현 | 남은 부분 |
|---|---|---|
| 비회원 비교 | 공개 추천·계산기·챗봇·카탈로그 | 입력을 모르는 경우의 결과 안내를 D-14에 맞춰 검수 |
| 내 통신비 | 현재 요금제 설정·변경 시점 계산 | 실제 청구액·약정/가족결합·출처를 비교에 일관되게 반영 |
| 내 구독 | 본인 구독 조회·등록·삭제, 입력 월요금 | 서비스별 실제 이용 여부·다음 결제일 등 필요한 필드만 단계적으로 추가 |
| 절약할 항목 | 중복 결제 3규칙, 번들·요금제 비교 | 사용자 확인한 실행 여부 및 실제 절약과 예상 절약 구분 |
| 결제내역 가져오기 | Mock 승인내역 검증·가맹점 식별 | 재업로드 중복 방지, 미인식 확인, 티어/구독 등록 확인 흐름 |
| 계정 설정 | 동의·탈퇴·로그인 방법 연결·세션 회수 | 회원 화면 연결·실제 Google/SMTP 운영 확인 |

회원 첫 화면은 ① 이번 달 통신비+구독료 ② 줄일 수 있는 비용(월·연) ③ 지금 할 일 순서로 구성한다.
이미 등록한 요금제·구독을 채우고 사용자가 수정하게 한다. 모르는 값은 건너뛰고 추정이라는 사실을 표시한다.
결과 카드와 펼쳐 보는 계산 근거는 필터·챗봇·계산기에서 공유한다.

회원 가입을 비교 시작 조건으로 두지 않고, **이 결과와 내 구독을 저장하는 순간** 로그인하도록 연결한다.
브라우저에는 비회원의 비민감 선택 조건만 임시 유지하고 토큰·실제 결제 원문을 보관하지 않는다.
저장 시점에 현재 회원을 다시 확인하며 클라이언트가 임의 userId를 지정하지 않는다.

금액의 의미를 먼저 정리해야 한다. 현재 변경 시점은 저장된 `monthly_price` 대신 카탈로그 티어 가격을 사용한다.
이를 실제 청구액 절감으로 표시하면 잘못된 확신을 준다. 실제 청구 기준과 카탈로그 가정 비교를 구분하고,
미확인 금액은 `ESTIMATED`, 사용자가 확정한 값은 `USER_PROVIDED`로 전달하는 계약을 제안한다.
총액·절감액은 기존 `pricing`에 입력을 전달해 계산하며 챗봇에 산술을 맡기지 않는다.

결제 파일에서 서비스가 식별돼도 티어·다음 결제일·정기 구독 여부가 확정된 것은 아니다.
가맹점을 억지로 매칭하거나 같은 지출을 자동 구독과 수기 구독에 이중 반영하지 않는다.
알림 발송·가족 공동 관리·장기간 대화 기억은 초기 개인화 범위에서 분리한다.

구현 순서는 **실제 지출/출처 정합 → 결제 가져오기 확인·중복 방지 → 회원 첫 화면 → 종료/결제일 알림**을 제안한다.
새 필드·엔드포인트는 `architecture.md §3` 계약과 AI 사본을 먼저 맞춘다.

## 4. 수익 모델

이번 사용자 요청으로 BM 검토를 재개한다. 기존 D-01을 과금·광고 구현 승인으로 자동 변경하지 않는다.

| 후보 | 적합성 | 조건/약점 | 제안 순서 |
|---|---|---|---|
| 실제 개통·가입 성과에 대한 제휴 수수료 | 절약을 실행하는 순간 수익 발생, 기본 비교는 무료 유지 가능 | 제휴 계약·개통 확인·취소 정산 필요. 더 비싼 상품 우대 유혹 | 초기 수익 실험 1순위 |
| 관리 편의 기능의 유료 멤버십 | 지속 관리의 가치를 직접 과금 | 절약하려는 사용자에게 구독료가 추가됨. 반복 이용 가치가 검증돼야 함 | 재방문이 확인된 뒤 |
| 기업용 계산 엔진·임직원 복지 도구 | 개인 과금 없이 고객사에 비용 청구 | 영업·지원 부담, 데이터 상업 이용 범위 확인 필요 | 장기 후보 |
| 결과 목록 광고·개인 데이터 판매 | 단기 매출 유인은 있으나 추천·개인정보 신뢰와 충돌 | 현재 제품 핵심에 부적합 | 채택하지 않는 안 권고 |

**권고: 기본 추천과 회원 기본 관리는 무료 → 투명한 성과형 제휴 실험 → 반복 사용이 확인되면 선택형 유료 기능.**
현재 제휴처·수수료·전환율이 확보됐다는 뜻은 아니며, 매출 전망 숫자를 확정하지 않는다.

제휴 도입 시 지킬 조건:

- 추천 순서는 실질월비용과 사용자 조건만 따른다. 수수료를 정렬이나 절감액에 입력하지 않는다.
- 비제휴 상품도 비교에 포함한다. 더 싼 비제휴 상품을 숨기지 않는다.
- 제휴 이동은 사용자가 선택하는 행동이며, 클릭 위치에서 수수료 발생 가능성을 설명한다.
- 상대 서비스로 회원의 구독 목록·결제 원문을 자동 전송하지 않는다.
- 유료 가입을 판단할 때도 서비스 이용료를 포함한 사용자 순편익을 보여준다. 실제 절약 확인 전 성공보수를 청구하지 않는다.

[Rocket Money의 공식 설명](https://www.rocketmoney.com/learn/personal-finance/what-is-rocket-money)은
무료 구독/지출 추적과 유료 관리 기능, 성공 시 비용이 발생하는 청구액 협상을 함께 소개한다.
이는 무료 비교·유료 실행 편의의 사례일 뿐, 한국 시장에서 요고비의 가격·수요를 검증하는 근거는 아니다.

먼저 측정할 것은 비교 완료율, 로그인 후 저장률, 30일 재방문, 절약 행동 완료와 사용자 확인 절약액이다.
제휴 실험의 손익은 **확정 개통 수 × 취소 차감 후 수수료 − 유입·지원·운영 비용**으로 확인한다.
클릭 수만으로 수익 가능성을 판단하지 않는다.

현재 README·데이터 문서는 비상업 교육 목적을 전제로 한다. 상업화 전 데이터별 이용 조건과 제휴 계약을
재확인해야 하며, 무료 공개 데이터라는 이유만으로 모든 제휴/유료 사용 권한이 확보됐다고 보지 않는다.

## 권고 실행 순서

1. CSV 갱신·역행 방지로 API 없이도 추천 가능한 데이터 기반을 확보한다.
2. 스마트초이스는 인증 오류를 해결하고 실제 성공 응답 → 검증 DB → 추천 표시 순서로 확인한다.
3. 회원이 입력한 실제 지출과 추천의 의미·출처를 먼저 맞추고 개인화 화면을 연결한다.
4. 기본 사용·절약 실행을 검증한 뒤 제휴 실험을 설계한다. 이번 주에 결제 시스템부터 만들지 않는다.
