# 카탈로그 원본은 CSV, 결손은 AI가 채운다 (기획 변경안)

> 소스·가격 반영 정책은 이후 D-18로 대체됐다. 현재 구현과 운영 절차는 [CSV 카탈로그 운영](../catalog-data.md)을 따른다. 아래는 당시 검토 이력이다.

2026-09-15 사용자 결정. **D-13의 "AI는 오프라인 추출만"을 대체**하고 D-05(런타임 크롤링 금지)의
경계를 다시 긋는다. 확정된 결정은 `docs/project.md` D-17, 이 문서는 근거와 설계다.

기존 결정과 겹치는 부분은 다시 적지 않는다 — 카탈로그 원본이 CSV라는 것은 이미 **D-16**이다.
이 문서가 새로 정하는 것은 **"CSV에 없는 것을 어떻게 다루는가"** 하나뿐이다.

---

## 1. 지금 무엇이 문제인가 (코드 기준 사실)

사용자가 카탈로그에 없는 구독 서비스를 물으면 **400으로 막힌다.**

| 경로 | 현재 동작 | 코드 |
|---|---|---|
| 필터 | 없는 `serviceId` → 400 `YGB-REQ-001` | `RecommendationService.java:50` |
| 챗봇 | AI가 이름→ID 변환 실패 또는 없는 ID → 같은 400 | `ChatController.java:51` |
| 요금제 | 조건 맞는 후보 0건 → 422 `YGB-CAL-001` | `RecommendationService.java:64` |

**절대 원칙 5-① 위반이다.** "모르면 막히는 화면을 만들지 않는다"고 해놓고, 정작 우리 CSV에
없으면 사용자가 막힌다. 사용자는 자기가 아는 서비스 이름을 댔을 뿐인데 실패 화면을 본다.

지금은 이걸 "데이터가 부족하다"로 넘겼지만, CSV가 원본인 이상 **결손은 상시 상태**다.
MNO 3사 전체 카탈로그 공개 API가 없고(D-16), 팀이 수기로 모으는 속도에는 한계가 있다.

---

## 2. 확정된 네 가지

| 질문 | 결정 |
|---|---|
| AI가 가져온 값의 지위 | **표시만, 계산 제외.** `ESTIMATED`로 붙이고 추천 순위·총액 계산에 넣지 않는다 |
| 호출 시점 | **비동기 트리거 + 다음 요청 반영.** 요청 경로 안에서 외부를 호출하지 않는다 |
| 검증 | **출처 URL+수집시각 필수 · 서로 다른 소스 2곳 일치 · 형식/범위 검사** 세 개 모두 |
| 일정 | **동결(9/17) 후 P2.** 동결 전에는 결손을 "막힘"이 아닌 "확인 중"으로 바꾸는 것까지만 |

세 검증을 모두 통과해야 사용자에게 보인다. 스마트초이스 시세 대조는 검증 조건에서 뺐다 —
스냅샷은 (통신사, 요금제명)이 맞아야 잡히는데, 애초에 우리 카탈로그에 없는 것을 찾는 상황이라
대부분 매칭되지 않는다. 잡히면 참고로 덧붙이되 통과 조건으로 쓰지 않는다.

## 3. 파이프라인

```
사용자 요청
   │
   ├─ CSV에 있음 → 기존 그대로 (OFFICIAL/DERIVED, pricing 계산, 추천 순위에 포함)
   │
   └─ CSV에 없음
        │
        ├─ 즉시: "확인 중" 응답 + 결손 기록 (요청은 여기서 끝난다. 외부 호출 없음)
        │
        └─ 비동기: AI 수집 → 검증 3단계 → 통과분만 catalog_candidate 에 ESTIMATED 로 저장
                                          │
                                          └─ 다음 요청부터 "참고" 영역에 표시 (계산·정렬 제외)
                                                │
                                                └─ 사용자가 금액을 고침 → USER_PROVIDED 승격
                                                     → 그때부터 계산에 들어간다 (기존 계산기 경로)
```

핵심은 **두 갈래가 절대 섞이지 않는다**는 것이다. 계산에 들어가는 값은 여전히 CSV(+사용자 확정)뿐이고,
AI가 가져온 값은 화면 옆자리에만 앉는다. 사용자가 손으로 확인해 승격시켜야 계산 경로로 넘어온다.

### 왜 비동기인가

요청 중 외부 호출은 세 가지를 동시에 깨뜨린다. ① 응답이 수 초~수십 초로 늘어난다 ② 외부 장애가
사용자 요청 실패가 된다 ③ D-05의 "데모 중 외부 구조 변경 시 발표 중단" 위험이 그대로 돌아온다.
비동기면 **요청 경로는 지금과 똑같이 CSV만 읽는다** — 장애 격리도 응답 시간도 건드리지 않는다.

대가는 "처음 물어본 사람은 못 본다"는 것. 그래서 첫 응답이 실패(400)가 아니라 **"확인 중"** 이어야 한다.
이게 동결 전에 할 몫이다 (§7).

## 4. 검증 게이트 — 세 단계 모두 통과해야 표시

| # | 게이트 | 규칙 | 실패 시 |
|---|---|---|---|
| 1 | 출처 | `source_url` 과 `collected_at` 이 모두 있어야 한다. AI가 출처 없이 "아는 값"을 답하면 버린다 | 폐기 |
| 2 | 형식·범위 | 기본료 > 0, 데이터 MB 정수, 망 종류 enum, 금액 상한(예: 월 30만원) 초과 배제 | 폐기 |
| 3 | 2소스 일치 | 서로 다른 도메인의 출처 2곳에서 **같은 값**을 얻어야 한다 | 보류(`PENDING`), 표시 안 함 |

게이트 2는 기존 DB CHECK 제약(`base_price > 0` 등)과 같은 규칙이다 — 새로 발명하지 않고 재사용한다.
게이트 3의 "같은 값"은 금액 기준 **완전 일치**로 시작한다. 허용 오차를 두면 "얼마까지 봐줄 것인가"가
곧바로 다음 논쟁이 되고, 그 답은 실제 수집 데이터를 보기 전에는 정할 수 없다.

**AI는 판정하지 않는다.** 세 게이트는 전부 BE의 결정적(deterministic) 코드다. AI는 후보와 출처를
가져오는 역할까지고, 통과/탈락은 우리가 정한 규칙이 자른다. 절대 원칙 2("AI 서버는 숫자를 만들지
않는다")를 지키는 방식이 이것이다 — AI는 숫자를 **옮기고**, 만들거나 고르지 않는다.

## 5. 데이터 모델 최소안 (P2)

테이블 하나로 끝낸다. "무엇이 없었나"(결손)와 "무엇을 가져왔나"(후보)를 **같은 행의 상태 변화**로 본다.

```sql
-- V9 (P2). 결손 요청 → 수집 후보 → 검증 결과를 한 행으로 추적한다.
CREATE TABLE catalog_candidate (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    kind          TEXT NOT NULL CHECK (kind IN ('MOBILE_PLAN', 'SUBSCRIPTION_TIER')),
    query_text    TEXT NOT NULL,          -- 사용자가 실제로 댄 말 ("쿠팡플레이", "요고 39")
    status        TEXT NOT NULL CHECK (status IN ('REQUESTED','PENDING','VERIFIED','REJECTED')),
    requested_cnt INT  NOT NULL DEFAULT 1, -- 몇 명이 찾았나 = 수집 우선순위
    base_price    BIGINT CHECK (base_price > 0),
    payload       JSONB,                   -- kind 별 나머지 필드(데이터MB·망·티어명 등)
    source_url    TEXT,
    source_url_2  TEXT,                    -- 게이트 3: 서로 다른 도메인
    collected_at  DATE,
    rejected_note TEXT,                    -- 왜 떨어졌나 (사람이 읽는다)
    UNIQUE (kind, query_text)
);
```

- `REQUESTED` = 결손만 기록됨(수집 전). `PENDING` = 한 소스만 확보. `VERIFIED` = 표시 가능. `REJECTED` = 폐기.
- `requested_cnt` 가 곧 팀의 **CSV 수집 우선순위 목록**이다. 많이 찾는데 없는 것부터 사람이 채운다.
- `VERIFIED` 행은 `mobile_plan` / `subscription_tier` 로 **자동 승격하지 않는다.** 카탈로그 테이블에
  들어가는 순간 계산 대상이 되기 때문이다. 승격은 사람이 CSV에 반영할 때만 일어난다.

`payload` 를 JSONB로 둔 이유: 두 kind의 필드가 다른데 P2 시점에 컬럼을 확정할 근거가 없다. 실제
수집 결과를 본 뒤 굳는다. <!-- ponytail: JSONB 한 칸, 필드가 굳으면 컬럼으로 승격 -->

## 6. 계약 변경 제안 (승인 필요)

`docs/architecture.md` §3은 사람이 관리한다(D-06). 아래는 **제안이며 아직 적지 않았다.**
AI 레포 사본(`AI-/docs/contract.md`)도 같은 날 맞춰야 한다.

### BE → AI (신규)

| Method | Path | 설명 |
|---|---|---|
| POST | `/sources/lookup` | `{kind, queryText}` → `{candidates:[{value, sourceUrl, collectedAt}]}` |

AI는 **후보 목록과 출처만** 돌려준다. 확정값 하나를 고르지 않고, 신뢰도 점수도 내지 않는다.
고르는 것은 BE의 게이트 3(2소스 일치)이다. 내부 토큰(`AI_INTERNAL_TOKEN`) 필수, 기존 게이트웨이 규약 동일.

### BE → 프론트 (신규)

| Method | Path | 설명 |
|---|---|---|
| GET | `/api/v1/catalog/candidates?kind=&query=` | 검증 통과 후보 조회 — `ESTIMATED` 고정, 계산 미사용 |

추천 응답(`CostResult`)에는 **넣지 않는다.** 같은 배열에 들어가는 순간 프론트가 정렬·합산에 섞을
위험이 생긴다. 별도 엔드포인트·별도 화면 영역으로 분리한다.

## 7. 범위와 순서

### 동결(9/17) 전 — 코드 변경 최소

1. **결손이 400이 아니게 한다.** 없는 서비스/요금제 요청을 `MissingInput` 계열 안내로 바꾼다.
   (`RecommendationService.java:50`, `:64`) — 절대 원칙 5-① 위반을 먼저 막는다. 외부 호출 없음.
2. 결손을 기록만 한다(`catalog_candidate` `REQUESTED`). 수집기는 붙이지 않는다.

이 둘만으로 "막히는 화면"이 사라지고, **팀이 채워야 할 목록이 데이터로 쌓이기 시작한다.**

### 동결 후 P2

3. AI `/sources/lookup` 계약 승인 → 게이트웨이 확장
4. 검증 3단계 + 비동기 수집기(`@Scheduled`)
5. `GET /catalog/candidates` + 화면의 "참고" 영역
6. 사용자 수정 → `USER_PROVIDED` 승격 경로

## 8. 유지되는 것 / 바뀌는 것

| | 내용 |
|---|---|
| **유지** | 절대 원칙 1~5 전부. 금액 계산은 `pricing` 단독(D-03), 미사용 혜택 0원(D-02), 엔드포인트 하나(원칙 3), Provenance(원칙 4) |
| **유지** | D-16 — 요금제 카탈로그의 원본은 CSV. AI 수집분은 카탈로그가 **아니다** |
| **유지** | D-05의 목적(데모 중 외부 의존 차단). 요청 경로에서 외부를 호출하지 않으므로 목적은 그대로다 |
| **변경** | D-13 "AI는 오프라인 추출만" → **비동기 수집 허용.** 단 표시 전용, 계산 제외 |
| **변경** | 결손 = 오류(400) → 결손 = 기록 대상 + 안내 |

## 9. 하지 않는 것

- **자동 승격 없음.** `VERIFIED` 가 `mobile_plan` 으로 저절로 들어가지 않는다. 계산 대상은 사람이 정한다.
- **요청 중 외부 호출 없음.** 어떤 경우에도 사용자 요청이 외부 응답을 기다리지 않는다.
- **AI 신뢰도 점수 없음.** 통과/탈락은 결정적 규칙이 자른다. "AI가 0.9로 확신함"은 근거가 아니다.
- **허용 오차 없음(초기).** 2소스는 완전 일치부터 시작한다. 완화가 필요하면 실제 데이터를 근거로 제안한다.
- **크롤러 없음.** AI가 외부에서 무엇을 어떻게 읽는지는 AI 레포의 몫이고, BE는 출처 URL과 값만 본다.

## 10. 남은 위험

- **2소스 일치의 실패율을 모른다.** 두 곳에서 같은 금액이 나오는 비율이 낮으면 `VERIFIED` 가 거의 안
  생기고 기능이 사실상 비게 된다. 실제 수집 전에는 알 수 없다 — P2 1주차에 표본으로 먼저 잰다.
- **"확인 중" 안내의 문구·재방문 유도가 미정.** 사용자가 다시 올 이유를 주지 못하면 결손 기록만 쌓인다.
- **출처의 신선도.** `collected_at` 은 남기지만 만료 정책(며칠 지나면 다시 수집)은 정하지 않았다.
