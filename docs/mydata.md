# 마이데이터 — 왜 라이브 연동을 안 넣었나

결정: **라이브 마이데이터 API 연동은 하지 않는다.** 근거·대안·전환 경로를 여기 정리한다.
관련 결정: `project.md` D-04, 데이터 판정 `data.md §5`. 이 문서는 그 상세 근거다.
**업로드조차 번거로워 직접 입력을 주 경로로 삼았다(D-33)** — 무엇을 묻는지는 [사용자 입력](user-inputs.md).

## 한 줄 결론
마이데이터는 (1) 우리가 지금 푸는 **요금제 카탈로그** 문제와 무관하고, (2) 라이브 API로 대신 조회하려면 **허가/지정**이 필요해 팀으로는 불가하며, (3) 쓸 수 있는 형태(**본인전송 업로드**)는 이미 로드맵에 있다. 그래서 별도 "마이데이터 연동"을 새로 파지 않는다.

## 이유 1 — 카탈로그와 다른 범주
- **마이데이터 = 사용자 "본인" 데이터**(내 요금제·내 청구액·내 사용량·내 구독·내 결제).
- **카탈로그 = 시장 전체 상품**(SKT/KT/LGU+/알뜰폰 *모든* 요금제·가격).
- 마이데이터로는 내가 쓰는 요금제 1개만 알 수 있고 **추천 후보가 될 전체 요금제 목록은 못 얻는다.** 카탈로그는 우체국 API + CSV + 사용자 입력으로 채운다(`data.md`, D-13).

## 이유 2 — 라이브 연동은 법적으로 불가 (D-04)
- **제3자 전송(우리가 API로 사용자 데이터를 대신 조회)**: 개인정보 마이데이터는 **전문기관 지정** 또는 일반수신자 등록, 금융 마이데이터는 **본인신용정보관리업 허가**가 필요하다. **법인이 아닌 팀 프로젝트로는 불가능**하고, 3주 일정 안에 확보할 수도 없다.
- 마이데이터 종합포털의 지원 API도 **허가받은 마이데이터 사업자**만 호출한다. 우리는 대상이 아니다.

## 이유 3 — 온보딩 "스킵" 효과도 부분적
자동 채움으로 줄일 수 있는 건 **사실 데이터**뿐이다:
| 입력 | 자동 채움 가능? |
|---|---|
| 사용량(GB)·현재 통신사/요금제/청구액 | ✅ (통신 마이데이터) |
| 현재 구독·결제 내역 | ✅ (금융 마이데이터) |
| **원하는 서비스 목록(선호)** | ❌ **불가** |

마이데이터는 사용자가 *가진 것(HAVE)* 만 알려주지 *원하는 것(WANT)* 은 모른다. 요고비의 차별점 **"미사용 혜택 0원"** 은 원하는 서비스 집합 S를 알아야 성립하므로, 마이데이터가 있어도 **이 입력은 사용자가 직접 골라야 한다.** 온보딩이 0이 되지 않는다.

## 대신 하는 것 — 본인전송 업로드 (채택)
- 2026년 개정 시행령으로 **개인이 직접 내려받아 관리**하는 본인전송 경로가 열렸다(`data.md §5`).
- 우리 구현: 사용자가 통신사·카드사에서 내려받은 정보를 **업로드**(`.eml`/OCR/수기, `data.md §4`, D8). `PaymentHistoryProvider` 뒤에 구현체를 둔다.
- **이것이 사실상 "마이데이터 본인전송"의 실용 버전이다** — 라이브 API가 아니라 업로드일 뿐.

### 업로드 방식의 메리트/한계
- **메리트(정확도가 핵심)**: 정확한 티어(`TIER_DUPLICATE` 정확), 다음 결제일(Phase2 프로모션 종료 알림이 입력 없이 성립), 사용자가 부정확하게 기억하는 요금·사용량 제거.
- **한계**: 사용자 다운로드→업로드 스텝이 남는다(완전 자동 아님). 선호(원하는 서비스)는 여전히 수동.
- 모든 업로드 추출값은 `ESTIMATED`로 표기하고 사용자 확인 후 계산에 넣는다(D-13 provenance).

## 전환 경로 (미래)
전문기관 지정/본인신용정보관리업 허가를 확보하면, **`PaymentHistoryProvider` 구현체 하나만 추가**해 제3자 전송 방식으로 전환할 수 있다(D-04). 즉 구조는 이미 열어뒀고, 지금은 자격 문제로 라이브 연동만 미룬 것이다.

## 스코프 판정
라이브 마이데이터 연동은 **스코프 밖**(D-04). 카탈로그엔 애초에 안 맞고, 개인 데이터는 본인전송 업로드로 커버한다.
