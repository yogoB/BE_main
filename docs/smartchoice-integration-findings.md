# 스마트초이스 연동 실패 원인과 검증 기록

최종 조사: 2026-09-16 KST. D-18의 스마트초이스 제거는 '스마트초이스 이중 검증 오버레이 복구' 결정으로 대체됨.
**현재 상태는 §9:** 로컬 키·Java 어댑터가 교정됐고 실제 API 조회·Java 파싱이 성공한다. 추천/배치 자동 검증 배선은 아직 없다.
§1~8은 오전의 원인 규명 기록이다. 그때의 '현재 키'·'미복구'는 당시 상태이며 이후 복구 결과는 §9와 구분한다.
**조사 상태: 키 거부의 근본 원인 확정. 공식 발급 키로 실제 요금제 8건을 두 번 수신했다.**

## 1. 최종 결론

**키 거부의 근본 원인은 `.env`의 자격증명 오입력이다. 공식 발급 키에서 문자 한 개가 누락됐다.**
PC 사이트 로그인 후 인증키 관리 화면의 발급값과 로컬 설정을 직접 대조해 불일치를 확인했다.
같은 HTTPS 주소·메서드·조회 조건·회선에서 키만 바꾸는 A–B–A–B 시험을 실행했다.

| 순서 | 사용한 키 | HTTP | 결과 코드 | 보고 건수 / 실제 요금제 이름 필드 |
|---|---|---|---|---|
| A1 | 기존 로컬 설정값 | 200 | 001 | 0 / 0 |
| B1 | 공식 관리 화면의 발급값 | 200 | 100 | 8 / 8 |
| A2 | 기존 로컬 설정값 | 200 | 001 | 0 / 0 |
| B2 | 공식 관리 화면의 발급값 | 200 | 100 | 8 / 8 |

**발급 키 자체의 미승인·만료·회선 차단이 아니라 잘못 복사된 키를 전송한 것이 이번 001의 원인이다.**
단순 시간 경과나 호스트 교체 때문이라는 설명도 같은 요청의 교차 재현으로 배제했다.
누가 언제 키를 잘못 복사했는지는 변경 이력이 없어 알 수 없으며, 원인 규명에 필요한 API 실패 분기는 위 시험으로 확인했다.

키와 별개로 **기본 URL의 경로 오류**도 있었다.
제거 직전 `SmartChoiceClient` 기본값은 `https://api.smartchoice.or.kr/openAPI.xml`이었다.
현재 로컬 설정에는 URL 재정의가 없으며, 이 경로는 키 유무와 관계없이 404다.
이번 시험에서 XML을 반환한 경로는 `/api/openAPI.xml`이다.
주소만 바꾸고 오입력 키를 유지하면 **404 → HTTP 200·001·0건**이 된다.
주소와 키를 바로잡은 시험에서는 HTTP 200·100·8건이 반환됐다.

또한 **실제 성공 XML과 기존 Java 파서의 태그 불일치**, **진단 스크립트의 성공 오판 결함**을 확인했다.
실제 성공도 `result_code=100`인데 기존 파서는 `resultCode`를 읽어 빈 목록을 반환한다.
HTTP 200과 `<result` 문자열만으로 성공을 판정해 `<result_code>001</result_code>`도 성공으로 출력한다.
실제 성공 데이터 없이 “정상 응답”이라고 판단할 수 있었던 원인을 재현했다. 현재 이 스크립트는 제거됐다.

모바일 로그인에서 별도로 500 화면이 발생했지만 **PC 로그인은 성공**했고 발급 키로 API도 성공했다.
모바일 로그인 장애를 API 거부의 원인으로 연결하지 않는다.
아래는 원인을 분리한 검증 기록이며 현재 D-18 정책이나 서비스 코드의 복구를 뜻하지 않는다.

### 로컬 키 설정 확인

기존 키는 .env에 한 번 정의됐고 프로세스 환경변수의 덮어쓰기는 없었다.
ASCII 영숫자이며 공백·퍼센트 인코딩·따옴표 문제를 발견하지 못했다.
`urlencode` → `parse_qs` 결과가 원래 키와 같은지 검사했다.
이는 로컬 직렬화의 보존을 확인한 것이며, 공급자 애플리케이션이 같은 값을 수신했다는 서버 로그 증거를 대신하지 않는다.
키 길이·일부 문자도 문서에 공개하지 않는다.
공식 관리 화면의 발급값과 비교한 결과 **문자 한 개 누락**을 확인했다. 공백·인코딩 검사만으로는 이 오입력을 찾을 수 없었다.
발급 키는 숨김 입력으로 진단 프로세스에 전달하고 저장하지 않았다. 기존 키/발급 키 어느 것도 증거 JSON에 포함하지 않았다.

### 키만 바꾼 최종 대조 (#17~20)

주소는 `https://api.smartchoice.or.kr/api/openAPI.xml`, GET·조회 조건·회선은 모두 동일하다.
§1 표의 A1/B1/A2/B2가 각각 증거 JSON의 `key_abab_1_configured`~`key_abab_4_issued`다.
발급 키 요청 두 번 모두 100·8건, 기존 키 두 번 모두 001·0건이었다.
성공 XML은 `root/items/item` 구조에 `result_code`, `result_count`, `v_plan_name`, `v_plan_price`,
`v_plan_display_data` 등을 포함했다. 실제 성공 태그 목록은 JSON에 보존했다.
8개 이름 필드 수신은 검증했지만 상품의 최신성·가격/약관 정확성·전체 카탈로그 완전성·DB 적재까지 검증한 것은 아니다.

## 4. 코드 수준 원인 검증

### 기본 주소 선택

제거 직전 클라이언트 설정:

```java
@Value("${SMARTCHOICE_API_URL:https://api.smartchoice.or.kr/openAPI.xml}") String baseUrl
```

application.properties는 .env를 읽고 현재 .env에는 해당 URL 재정의가 없다.
이 코드와 현재 설정의 조합은 404 경로를 선택한다. 과거 다른 배포 환경의 설정까지 확인한 것은 아니다.
공식 문서의 주소 불일치가 개발자의 선택에 영향을 주었는지는 추정으로만 남긴다.

### 진단 스크립트의 잘못된 성공 판정

삭제된 scripts/check_smartchoice.sh의 조건:

```bash
[ "$code" = "200" ] && grep -qiE '<(Plan|item|result)' "$out"
```

이 정규식은 오류의 `<result_code>`에도 일치한다. 200·001·0건 입력으로 성공 분기에 들어가는 것을 재현했다.
TCP 연결 후 응답이 없다는 이유로 IP 미등록을 우선 원인으로 표시하던 진단에도 공급자 로그 근거가 없었다.
과거 이 스크립트의 “정상 응답”·“IP 문제” 출력은 원인 확정의 증거로 사용하지 않는다.

### resultCode 조건문은 뒤집으면 안 됨

```java
if (!"100".equals(firstText(doc, "resultCode"))) {
    return List.of();
}
```

성공 코드가 아니면 결과를 사용하지 않는 올바른 방어 조건이다.
오류 XML의 태그는 result_code여서 기존 조회는 null이 된다.
하지만 태그를 맞춰도 값이 **001이므로 여전히 실패로 처리해야 한다.**
부정 연산자를 제거하거나 오류를 성공으로 취급하면 인증 문제를 해결하지 못하고 잘못된 결과만 허용한다.

기존 셸 정규식·Java 성공 조건을 Python으로 재현한 검증 결과:

| 입력 | 기존 셸 진단 | 기존 Java 성공 조건 | 정규화된 태그 + 성공 코드 + 요금제 이름 |
|---|---|---|---|
| result_code=001, 0건 | 잘못 성공 | 실패 | 실패 |
| 합성 result_code=100, 1건 | 성공 | 잘못 실패 | 성공 |
| 합성 resultCode=100, 1건 | 성공 | 성공 | 성공 |

위 두 성공 입력은 **합성 XML**이며 공급자의 실제 성공 응답이 아니다.
Java 전체 클래스 재컴파일/통합 테스트가 아니라 조건식의 재현이다.
**후속 실요청 B1·B2에서는 성공 태그도 result_code임을 확인했다.** 따라서 기존 resultCode 조회가 null이 되어
정상 데이터도 빈 목록으로 버리는 결함이 실제 계약 차이로 확정됐다.
실제 데이터 표시는 v_plan_display_data인데 기존 v_display_data 조회는 빈 문자열이 된다.
기존 mock은 resultCode=100과 v_display_data를 사용해 외부 승인·주소·실계약을 검증하지 못했다.
이번 실제 응답은 8건이므로 “호출당 항상 3건”이라는 이전 코드 주석도 계약으로 가정하면 안 된다.

## 5. 공식 문서 대조와 이전 설명 정정

2026-09-16 로컬에서 공식 안내를 **HTTPS 200으로 직접 수신**했다.
앞선 웹 조회 도구의 타임아웃은 사이트 폐쇄 증거가 아니다.

- [현재 안내](https://www.smartchoice.or.kr/smc/openapi/openapiguide_02.do?type=m)는 요청주소 /openAPI.xml과 예제 /api/openAPI.xml이 다르다.
- 표의 Voice/Age/Dls와 예제의 voice/age/dis도 다르다.
  [모바일 도메인 안내 검색 색인](https://m.smartchoice.or.kr/smc/openapi/openapiguide_02.do)은 소문자 명세를 쓴다.
- 데이터 표시 필드는 현재 페이지가 v_plan_display_data, 모바일 도메인 색인은 v_display_data다.
  **기존 문서에서 v_display_data를 공식 명세와 다르다고 한 설명은 한 문서 버전에 한정된다.**
  후속 성공 실응답에서 v_plan_display_data를 확인해 현재 검증한 실제 계약 기준으로 기존 필드 매핑 오류를 확정했다.
- [발급 관리 안내](https://www.smartchoice.or.kr/smc/openapi/openapiguide_03.do)는 로그인·신청·심사·발급 절차를 제시한다.
  회원 가입·키 문자열 보유·승인·현재 사용 가능 상태를 혼동하지 않는다.

## 6. 공식 로그인 장애

사용자가 관리 화면에서 직접 로그인한 뒤 제공한 이미지에 500 내부 오류와 오류 문서 처리 중 추가 400 오류가 표시됐다.
브라우저 탭의 실제 주소는 **https://m.smartchoice.or.kr/smc/member/loginOk.do**, 제목은 **500 500**이었다.
비밀번호/로그인 요청 본문/쿠키는 조회하거나 저장하지 않았다.

이는 요고비 서버의 로그인 실패가 아니라 **스마트초이스 모바일 로그인 처리 경로의 오류 화면**이다.
브라우저 화면과 URL을 확인했으며 원래 로그인 POST의 네트워크 상태 코드를 별도 캡처한 것은 아니다.
DB 장애·배포 오류·WAF·세션 처리 중 무엇이 원인인지는 화면만으로 판정할 수 없다.
추가 400은 화면상 오류 문서 처리 중 발생한 것으로, 이를 사용자의 비밀번호 오입력 증거로 해석하지 않는다.

모바일 경로만의 문제인지 확인하려고 PC 도메인의 공식 관리 화면을 별도 탭으로 열었다.
사용자가 PC 로그인에 성공했고 관리 화면의 로그아웃 메뉴·발급 키 정보·이용통계를 직접 확인했다.
그 발급 키로 별도 HTTP 클라이언트의 API 조회도 성공했다. 인증 쿠키 없이 키만으로 성공한 요청이다.
**모바일 로그인 장애의 내부 원인은 별도 공급자 이슈다. 이번 API 키 거부 원인은 로컬 오입력으로 확정했다.**

## 7. RCA 판정과 재발 방지

이번 종료 기준은 ① 공식 발급값 대조 ② 원인 한 요소만 바꾼 대조 ③ 실패·성공의 교차 재현
④ 성공 코드와 실제 요금제 수신이다. **키 한 문자 누락을 확인하고 001/100/001/100 및 0/8/0/8건으로 모두 충족했다.**
최종 원인은 “스마트초이스 API가 전반적으로 동작하지 않는다”가 아니라 아래 순서의 로컬 연동 결함이다.

1. 기본 주소에 /api가 없어 404.
2. /api를 포함한 주소에서도 오입력 키로 001.
3. 올바른 발급 키로 받은 성공 XML도 기존 Java 파서의 resultCode 조회 때문에 빈 목록 처리.
4. 별도 셸 진단은 오류 XML조차 성공으로 표시해 실제 연동 확인을 방해.

재연동을 별도로 결정한다면 발급값을 직접 복사하고, 검증된 HTTPS 주소·실응답 태그로 맞춘 뒤
비밀정보를 제거한 실제 응답 fixture로 오류/성공을 모두 검증한다.
HTTP 200·키 문자열 존재·mock 통과를 실연동 완료 기준으로 쓰지 않는다.
오류 코드를 보존해 인증 실패·통신 실패·실제 결과 없음도 구분해야 한다.
키 값을 로그에 추가하는 방식으로 진단하지 않는다.

**이번에는 원인 규명만 수행했다.** .env와 서비스 코드는 수정하지 않았고, 기존 발급 키를 재발급/삭제하지 않았다.
서비스 복구를 완료했다고 주장하지 않는다. 새 라이브러리나 자동 수집기도 추가하지 않았다.
