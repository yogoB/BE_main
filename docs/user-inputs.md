# 사용자 입력 — 무엇을 왜 직접 묻는가

> 결정: `project.md` D-33. 마이데이터 판정은 D-04·`mydata.md`, 화면 규칙은 절대 원칙 5와 `../UX_POLICY.md`.
> 마지막 갱신: 2026-09-16

## 1. 결론

**파일을 내려받아 올리게 하지 않는다. 우리가 여러 번 묻는다.**

제도상 우리가 쓸 수 있는 개인 데이터 경로는 **본인전송**뿐이다(제3자 전송은 허가·지정이 필요해 불가, D-04).
그런데 본인전송은 사용자가 *통신사/카드사 사이트에 로그인 → 내역 조회 → 파일 내려받기 → 우리에게 업로드*를
해야 한다. 추천 한 번 받으려고 하기에는 너무 무겁고, 거기서 대부분 이탈한다.

그래서 **번거로움을 우리가 진다.**

| | 파일 업로드 경로 | 직접 입력 경로(주 경로) |
|---|---|---|
| 사용자가 하는 일 | 외부 사이트 로그인·조회·다운로드·업로드 | 화면에서 고르기(대부분 객관식) |
| 실패 지점 | 파일 못 찾음·형식 다름·중도 이탈 | 없음 — **모르면 "모름"으로 넘어간다** |
| 우리가 하는 일 | 파서 유지·형식 대응 | **질문을 잘게 쪼개고, 기본값을 채우고, 빠진 값의 영향을 설명** |
| 정확도 | 높음 | 입력한 만큼 정확(`accuracy` 로 표시) |
| 위치 | **보조**(원하는 사람만) | **기본** |

업로드(`.eml`·Mock 마이데이터)를 없애지는 않는다. 중복 결제 탐지처럼 **파일이 있어야 훨씬 좋아지는 기능**에서는
계속 쓴다. 다만 그것 없이도 추천·계산·변경 시점은 **끝까지 간다.**

## 2. 이 결정이 지키는 규칙

- **원칙 5-①** 모르면 막히는 화면을 만들지 않는다 → 모든 선택 입력에 "모름"이 있고, 그 경로로도 결과까지 간다.
  빠진 값은 `missingInputs`(field·impact·howToFind)로 **무엇이 덜 정확해지는지**와 **어디서 찾는지**를 함께 돌려준다.
- **원칙 5-②** 사용자가 아는 것만 묻는다 → 금액·기본값은 우리가 먼저 채우고(`ESTIMATED`), 사용자는 고치기만 한다.
  고치면 `USER_PROVIDED`로 승격돼 그때부터 계산 기준이 된다.
- **원칙 4** 모든 금액에 출처를 붙인다 → 사용자가 넣은 값도 예외가 아니다.

## 3. 우리가 묻는 인자 전체

### 3-1. 추천 — `POST /api/v1/recommendations`

| 인자 | 필수 | 모르면 | 화면에서 묻는 법 |
|---|---|---|---|
| `required.monthlyDataGb` | ✅ | 화면이 기본 10GB로 보내고 **"10GB 기준으로 계산했다"고 적는다** | 구간 선택(칩) |
| `required.wantedServiceIds` | ✅ | 없으면 추천이 성립하지 않는다(유일한 진짜 필수) | 서비스 카드 선택 |
| `optional.currentCarrier` | | 안내만. 단 결합 할인을 적었다면 **어디에도 반영하지 못한다**(G-29 c) | 통신사 검색 + 직접 입력. 브랜드 이름을 그대로 보낸다 — 카탈로그에 없으면 결손으로 쌓인다(2026-09-17 QA) |
| `optional.currentPlanId` | | '현재' 금액을 계산하지 않고 화면이 적은 값만 남는다 | 요금제 이름 검색(카탈로그 1,707건). 고르면 통신사도 함께 확정된다 |
| `optional.networkType` | | 망 필터 없이 계산 | 5G/LTE/3G + "잘 모르겠어요" |
| `optional.contractType` | | `missingInputs`: "선택약정 25% 적용 시 약 25% 절감 가능 / 통신사 마이페이지 > 약정 정보" | 무약정·선택약정·공시지원 + 모름 |
| `optional.hasFamilyBundle` · `familyBundleDiscountKrw` | | `missingInputs`: "결합 중이면 할인액을 알려주세요 / 통신사 앱 > 요금 청구서" | 예·아니오 + 회선 수·월 할인액. 할인액은 **현재 통신사 요금제에만** 반영된다(G-29) |

응답의 `accuracy`가 `FULL`/`PARTIAL`로 **얼마나 채웠는지**를 그대로 보여준다.

### 3-2. 계산기 — `POST /api/v1/calculator`

| 인자 | 필수 | 비고 |
|---|---|---|
| `planId` | ✅ | 사용자가 카탈로그에서 고른 값이라 없는 ID는 400(결손이 아니라 잘못된 요청) |
| `tierIds` | ✅ | 추천과 달리 **구독 등급을 직접 지정**한다(대표 등급 추정 없음) |
| `optional` | | 추천과 같은 네 가지 |

카탈로그에 금액이 없는 서비스(해외 결제 등)는 여기서 **직접 입력**해 바로 반영할 수 있다.

### 3-3. 변경 시점 — `GET /api/v1/me/switch-timing`

| 인자 | 기본값 | 모르면 |
|---|---|---|
| `targetPlanId` | — | 필수(어디로 옮길지) |
| `switchingCost` | `0` | **위약금은 사용자가 모르는 대표 항목이다.** 0으로 두면 "위약금 없이 계산한 회수 시점"이 나오고 화면이 그 사실을 적는다 |
| `remainingContractMonths` | `0` | 0이면 무약정으로 본다 |

현재 요금제·구독은 **저장된 회원 값**을 쓴다(아래 3-4).

### 3-4. 회원이 저장하는 값

| 무엇 | 인자 | 왜 받는가 |
|---|---|---|
| 현재 요금제 | `POST /me/current-plan` — `planId` | 변경 시점·절감액의 비교 기준 |
| 내 구독 | `POST /me/subscriptions` — `tierId`, `monthlyPrice` | **실제 결제액**을 받으면 카탈로그 정가 대신 그 값으로 계산한다(`USER_PROVIDED`) |
| 결제 내역(선택) | `POST /me/payments/import` — `.eml` 등 | 중복 결제 탐지용 **보조 경로**. 없어도 나머지는 동작 |

### 3-5. 화면이 추가로 받는 값(서버에 안 보내는 것 포함)

디테일 모드는 위 인자 외에 **현재 통신비**와 **약정 정보**를 더 묻는다.

| 무엇 | 쓰임 |
|---|---|
| 현재 월 통신비(구간 선택 또는 직접 입력) | "지금보다 얼마 아끼는지" 한 문장(원칙 5-③). **사용자 입력 합계이지 우리 계산값이 아니라고 화면에 적는다** |
| 약정 있음/없음 · 종료일 | 캘린더 일정 기준일, 변경 시점 안내 |
| 구독별 유지/해지 | 해지하기로 한 것은 추천 대상에서 뺀다(원칙 1) |

## 4. 묻는 방식의 규칙

1. **한 번에 하나씩 묻는다.** 긴 폼 하나가 아니라 단계로 쪼갠다(라이트/디테일 모드).
2. **객관식을 우선한다.** 금액·용량은 구간 칩으로 고르고, 필요할 때만 직접 입력을 연다.
3. **"모름"은 1급 선택지다.** 회색 글씨의 건너뛰기가 아니라 같은 크기의 버튼이다.
4. **모르면 그 자리에서 찾는 법을 준다.** 사용량 조회 경로는 통신사별로 화면에 그대로 노출한다(`data.md §8`).
5. **되묻지 않는다.** 같은 값을 두 화면에서 다시 묻지 않는다. 회원은 저장해 다음부터 건너뛴다.
6. **채운 값은 승격한다.** 프리필(`ESTIMATED`) → 사용자가 고침(`USER_PROVIDED`) → 계산 기준.

## 5. 아직 못 하는 것

- **자동 채움이 없다.** 사용자가 통신사 사이트에서 값을 옮겨 적어야 한다. 마이데이터 라이브 연동으로 없앨 수 있지만
  허가가 필요해 불가하다(D-04).
- **사용량 OCR은 선택 기능이다.** 스크린샷 → AI `/ocr` 경로는 있으나 추출값은 `ESTIMATED`이고 사용자 확인을 거친다.
- **비회원은 저장이 없다.** 새로고침하면 다시 묻는다(세션 저장까지만).
