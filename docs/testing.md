# 골든 케이스

**`pricing` 코드를 쓰기 전에 이 케이스를 테스트로 먼저 옮긴다.**
정답이 명시되지 않은 계산 로직을 구현하지 않는다.

LLM은 컴파일되지만 **금액이 틀린 코드**를 잘 만든다. "미사용 혜택 0원"처럼
상식과 어긋나는 규칙일수록 학습된 패턴으로 되돌아간다. 그 오류를 발표 당일에 발견하면 늦는다.

## G-01. 미사용 혜택 0원 — 순위 역전 ★최우선

**검증**: `CostCalculatorGoldenTest` · `RecommendationApiTest`

| | 원하는 서비스 | P1 | P2 | 정답 |
|---|---|---|---|---|
| a | {T2 넷플릭스} | 55,000 + **0** = 55,000 | 45,000 + 13,500 = 58,500 | **P1** |
| b | {T12 웨이브} | 55,000 + 10,900 = 65,900 | 45,000 + **0** = 45,000 | **P2** |

약정 없음 기준. 요금제 쌍은 그대로인데 원하는 서비스만 바꾸면 **순위가 뒤집혀야 한다.**

**G-01-b의 `CostBreakdown`에 "넷플릭스" 항목이 한 줄이라도 있으면 실패로 처리한다.**

## G-02. 선택약정 25%

**검증**: `CostCalculatorGoldenTest`

| | 기본료 | 약정 | 정답 |
|---|---|---|---|
| a | 55,000 | `SELECTIVE_25` | 41,250 |
| b | 55,000 | `NONE` | 55,000 |
| c | 33,333 | `SELECTIVE_25` | **24,999** |

c: `33,333 × 0.75 = 24,999.75` → **내림** → 24,999. 반올림(25,000)이면 실패.

## G-03. 할인 적용 순서

**검증**: `CostCalculatorGoldenTest`

기본료 55,000, 요금제 약정할인 4,800, 선택약정 25%.

```
1) 약정할인      55,000 - 4,800 = 50,200        (priority 100)
2) 선택약정 25%  floor(50,200 × 0.75) = 37,650  (priority 200)
```

정답 **37,650**. 순서를 바꾸면 36,450이 나온다. 1,200원 차이는 눈으로 안 보인다.

| 경로 | 구독료 |

| 개별 | 13,500 + 10,900 = 24,400 |

티빙·웨이브가 각각 별도 줄이면 실패.

## G-05. 택1(exclusive) 최적 선택

**검증**: `CostCalculatorGoldenTest`

## G-09. 중복 결제 탐지 (P1)

**검증**: `DuplicateDetectorGoldenTest` · `DetectionServiceTest`

| | 상황 | 정답 |
|---|---|---|
| a | P2(웨이브 무료) + 웨이브 10,900 결제 중 | `BENEFIT_OVERLAP`, 10,900 |
| b | 넷플 스탠다드 + 프리미엄 동시 결제 | `TIER_DUPLICATE`, 13,500 |
| c | 티빙 + 웨이브 개별 결제 | `BUNDLE_OVERLAP`, 9,400 |
| d | P1(넷플 무료) + **웨이브** 결제 중 | **탐지 없음** |
| e | 요금제가 그 서비스를 **`BUNDLE_INCLUDED`(등급 미상)** 로 포함 + 그 서비스 결제 중 | `BENEFIT_OVERLAP`, 내는 금액 전액, 출처 **`ESTIMATED`** |
| f | **`FIXED_DISCOUNT`**(등급 지정) + 정가로 결제 중 | `BENEFIT_OVERLAP`, `내는금액 − 혜택적용가`, 출처 **`DERIVED`** |
| g | f 인데 이미 혜택가 이하로 내는 중 | **탐지 없음**. 낭비가 0 이하면 낭비가 아니다 |

d가 중요하다. 혜택이 있어도 **다른 서비스**를 결제 중이면 중복이 아니다.

**e 를 추가한 이유(2026-09-17).** 운영에 실제로 이런 회원이 있었고 탐지가 침묵했다 —
현재 요금제가 KT `초이스 더블 유튜브 프리미엄+넷플릭스`(이름부터 넷플릭스 포함)인데
넷플릭스 광고형 스탠다드를 7,000원 따로 결제 중이었다. 그 혜택이 `BUNDLE_INCLUDED`·등급 미상이라
`benefitType == FREE` 검사에서 탈락했다. 운영 혜택 73행 중 **`BUNDLE_INCLUDED` 가 51행(70%)** 이므로
이 패턴이 통째로 새고 있었다.

**금액을 단정하지 않는다.** 등급을 모르면 얼마가 낭비인지 확정할 수 없다 — 전액일 수도, 상위 등급
차액만일 수도 있다. 그래서 e 의 출처는 `ESTIMATED` 이고 **표시 전용**이다(D-17). 추천 금액 계산에는
들어가지 않는다. 확정할 수 없다고 침묵하는 것보다 "확인해 보세요"가 사용자에게 낫다.

## G-11. 회수기간 (P2)

**검증**: `SwitchTimingGoldenTest`

| | 전환비용 | 월절감 | 약정잔여 | 회수 | 정답 |
|---|---|---|---|---|---|
| a | 60,000 | 17,700 | 10개월 | 4 | `SWITCH_NOW` |
| b | 60,000 | 17,700 | 2개월 | 4 | `WAIT_UNTIL_EXPIRY` |
| c | 60,000 | 0 | 10개월 | — | `NO_BENEFIT` |
| d | 0 | 17,700 | 10개월 | 0 | `SWITCH_NOW` |
| e | `Long.MAX_VALUE` | `Long.MAX_VALUE` | 10개월 | 1 | `SWITCH_NOW` (덧셈 오버플로 방지) |
| f | `Integer.MAX_VALUE + 1` | 1 | 10개월 | 범위 초과 | 계산 거부 (음수로 축소 변환 금지) |
| g | 60,000 | 17,700 | **0개월** | 4 | `SWITCH_NOW` (약정이 이미 끝났으면 기다릴 대상이 없다) |

`ceil(60,000/17,700) = ceil(3.389) = 4`. 내림으로 3이면 실패. c는 0 나눗셈 방어.
g는 약정 잔여 0이면 회수개월과 무관하게 `SWITCH_NOW` — `회수 < 잔여` 비교만 쓰면 `4 < 0` 이 거짓이라 "끝난 약정을 기다리라"는 결론이 나온다.
HTTP에서는 음수 전환비용·음수 약정잔여 및 회수 개월의 응답 정수 범위 초과를 400으로 반환한다.

## G-12. 카탈로그 결손은 막지 않는다 (D-17)

**검증**: `RecommendationApiTest`

CSV에 없는 것을 물어도 **오류를 내지 않는다.** 아는 것으로 계산하고, 모르는 것은 안내하고 기록한다.
절대 원칙 5-① — "모르면 막히는 화면을 만들지 않는다".

| | 입력 | 정답 |
|---|---|---|
| a | `wantedServiceIds=[1, 99]` (99는 없음) | **200**. 1로만 계산. `missingInputs`에 `wantedServiceIds` 항목, `accuracy=PARTIAL`. `catalog_candidate`에 `(SUBSCRIPTION_TIER, "serviceId:99", REQUESTED)` 1행 |
| b | `wantedServiceIds=[99]` (전부 없음) | **200**. 원하는 서비스 없이(혜택 0원) 기본료로 계산하며 **결과는 비지 않는다**. 99는 기록 |
| c | 조건 만족 요금제 0건 (`monthlyDataGb=200`) | **200**. `results=[]` + 안내. `(MOBILE_PLAN, "dataMb>=204800,network=ANY", REQUESTED)` 기록 |
| d | c를 한 번 더 요청 | 행이 늘지 않고 `requested_cnt=2` |
| e | `catalog_candidate`가 상한(10,000행)에 도달 | 기록하지 않는다. **요청은 그대로 200** — 공개 엔드포인트라 무한 증식을 막는다 |

이전 동작은 a·b가 **400** `YGB-REQ-001`, c가 **422** `YGB-CAL-001` 이었다. 둘 다 사용자를 막았다.
기록 실패(DB 오류)는 추천을 깨뜨리지 않는다 — fail-soft, 로그만 남기고 200을 유지한다.

## G-13. 메일 없이 가입 (D-20 · D-21) — **D-34 로 폐기 (2026-09-17)**

**검증**: **없음 — 폐기.** 옛 DirectSignupTest 는 삭제됐다(닉네임 부분만 `NicknameTest` 로 남았다)

> 가입 경로가 Google 하나가 되면서 자체 가입이 사라졌다. 아래 케이스는 **더 이상 검증하지 않는다** —
> DirectSignupTest 도 지웠다(닉네임 부분만 `NicknameTest` 로 옮겼다). 기록으로만 남긴다. 현재 가입 규칙은 G-17(아래)이다.

`{name, email, password, nickname}`으로 바로 가입한다. **가입 형태는 이것 하나뿐이다** —
메일 토큰 흐름은 2026-09-16 에 코드에서 제거했다.
**이메일 소유는 확인하지 않는다** — `email_verified`는 `FALSE`로 남고 로그인은 그 값을 보지 않는다.

| | 입력 | 정답 |
|---|---|---|
| a | 네 필드 정상 | **200** 가입 + 쿠키 발급. `email_verified=FALSE` |
| b | a 직후 같은 이메일로 다시 | **409** `YGB-AUTH-DUP-EMAIL` |
| c | a 직후 같은 닉네임·다른 이메일 | **409** `YGB-AUTH-DUP-NICK` |
| d | a로 가입한 계정으로 로그인 | **200** (미확인이어도 통과 — 확인할 방법이 없다) |
| e | 비밀번호 8자 미만 | **400** `YGB-REQ-001` |
| e2 | 숫자만(`12345678`) 또는 문자만(`abcdefgh`) | **400** — 문자와 숫자를 섞어야 한다 (사용자 결정 2026-09-16) |
| e3 | `abcd1234`(8자·혼합) | **200**. 72바이트 초과는 여전히 400(bcrypt 입력 한계) |
| f | `{token, password}` (옛 메일 토큰 형태) | **400** — `name`·`email` 누락. 토큰 가입은 없어졌다 |

b·c를 구분하는 이유: "이미 가입된 이메일"과 "이미 쓰는 닉네임"은 사용자가 할 일이 다르다.
**남는 위험**: 이메일 소유를 아무도 확인하지 않으므로 타인의 주소로 가입할 수 있다(`auth-security.md`).

## G-15. 복구 코드로 비밀번호 재설정 (D-22) — **D-34 로 폐기 (2026-09-17)**

**검증**: **없음 — 폐기.** 보관 사유는 아래 본문

> 우리가 회원 비밀번호를 보관하지 않으므로 재설정할 것이 없다. 아래 케이스는 더 이상 검증하지 않는다.
> **G-15h(복구 시 세션 폐기)만은 교훈으로 남긴다** — 명세는 맞았는데 코드가 지키지 않았고 강제하는 테스트가
> 없었다. 같은 실수를 막으려면 "문서에 적힌 보안 속성에는 반드시 테스트가 붙는다"를 지켜야 한다.

메일이 없으므로 **복구 코드**가 유일한 자기복구 수단이다. 가입 응답에 **한 번만** 나오고 서버는 해시만 갖는다.

| | 입력 | 정답 |
|---|---|---|
| a | 직접 가입 | 응답에 `recoveryCode` 1회 포함. DB 에는 **평문이 없다** |
| b | `{email, recoveryCode, newPassword}` 로 재설정 | 200 + **새 복구 코드** 발급. 기존 세션 전부 폐기 |
| c | b 직후 같은 코드로 다시 | **401** — 코드는 1회용이다 |
| d | 틀린 코드 | **401**. 존재하지 않는 이메일도 같은 응답(계정 존재를 알려주지 않는다) |
| e | 재설정한 새 비밀번호로 로그인 | 200 |
| f | 재설정 전 비밀번호로 로그인 | **401** |
| g | 같은 이메일로 코드 시도 10회 초과 | **429** (무차별 대입 방어) |
| h | 복구 **전에 열려 있던** 로그인 세션 | 전부 **401**. 남는 세션은 복구한 본인의 새 세션 하나뿐 |

b가 새 코드를 주는 이유: 한 번 쓰면 사라지므로 다음 복구 수단이 없어진다.
h를 따로 적는 이유: b의 "기존 세션 폐기"는 **2026-09-16까지 지켜지지 않았다.** `credential_version` 은
발급 시점에만 검사되는데(`AuthTokens.authenticate` 는 `auth_session` 만 본다) 코드가 그 값만 올리고
세션 행을 지우지 않아, 되찾아도 침입자 세션이 살아 있었다. 명세는 맞았고 이를 강제하는 테스트가 없었다.
`GET /me` 는 복구 코드를 **절대 돌려주지 않는다** — 로그인한 사람에게도 보여줄 이유가 없다.

## G-17. 해외 결제 구독 — 원화는 표시만, 계산은 사용자 금액 (사용자 결정 2026-09-16)

**검증**: `ForeignCurrencyCatalogTest` · `ExchangeRatesTest`

ChatGPT·Claude 처럼 **USD 로 파는 구독**을 카탈로그에 넣되 원화 금액을 지어내지 않는다.
환율은 하루 1회 배치로 받아 `fx_rate` 에 남기고, 화면에는 `$20 · 약 27,183원(추정)` 으로 **표시만** 한다.

| | 입력 | 정답 |
|---|---|---|
| a | `GET /catalog/services` 의 ChatGPT Plus | `price=20` · `currency="USD"` · `krwEstimate`= 환율 환산값 · `krwRateDate`= 기준일 |
| b | 같은 응답의 넷플릭스 광고형 스탠다드 | `price=7000` · `currency="KRW"` · `krwEstimate=null` · `krwRateDate=null` |
| c | `fx_rate` 에 USD 행이 없을 때 a | `krwEstimate=null` (0원으로 적지 않는다) |
| d | 추천 요청의 `wantedServiceIds` 에 ChatGPT | **200**. 결과는 나오고 `missingInputs` 에 "해외 결제라 … 계산에서 뺐어요" |
| e | d 의 ChatGPT | `catalog_candidate` 에 **기록하지 않는다** (결손이 아니라 사용자 확인 대상) |
| f | 계산기 `tierIds` 에 USD 등급 | **200**. 그 등급만 빼고 계산하고 같은 안내를 싣는다 |
| g | 계산기 `tierIds` 에 없는 ID | **400** (기존 동작 유지 — 잘못된 요청) |
| h | 환율 API 호출 실패 | 이전 값 유지. 화면은 계속 이전 기준일로 표시한다 |
| i | 환산 반올림 | **내림(floor)**. $20 × 1359.15 = 27,183원 |
| j | 표기가가 **세금 별도**인 등급(클로드 Pro) | `taxIncluded=false`. `krwEstimate` 는 부가세 10%를 더한 값 — $20 × 1.1 × 1359.15 = **29,901원** |
| k | 원화 등급 | `taxIncluded=true`. 표시가가 총액이므로 10%를 더하지 않는다 |

j 가 필요한 이유: 해외 사업자의 표기가는 세금 별도라 실제 결제액이 10% 더 크다(전자적 용역 공급 부가세).
표기가에 1.1을 곱해 **저장하면 출처가 사라지므로** 저장은 표기가 그대로 두고 `tax_included` 로 구분한다.

d·f 가 200 인 이유: 모르면 막지 않는다(절대 원칙 5-①). 금액을 지어내지 않으면서 결과는 보여준다.
**계산에 들어가는 유일한 경로**는 사용자가 마이페이지 > 내 구독에 넣은 실제 결제액(`USER_PROVIDED`)이다.

## G-18. 가입할 수 없는 요금제는 추천하지 않는다 (연령·자격 제한)

**검증**: `AgeLimitCandidateTest`

`mobile_plan.age_limit` 은 CSV·DB 에 채워져 있으나 **조회가 쓰지 않아** 40세 사용자에게 키즈 요금제가,
성인에게 청년 요금제가 후보로 들어갔다. 가입 자격이 없는 요금제를 1등으로 보여주면 사용자는

시드 실측 분포(1,706종): `ALL` 1,504 · `다이렉트` 44 · 나머지 158(키즈·청년·시니어·복지·외국인·군인·태블릿).

| 케이스 | age_limit | 기대 |
|---|---|---|
| a | `ALL` | 후보에 **포함** |
| b | `다이렉트` | 후보에 **포함** — 온라인 가입 채널일 뿐 자격 제한이 아니다. 요고 13종이 여기 속한다 |
| c | `NULL` | 후보에 **포함** — 수집되지 않은 값을 제한으로 해석하지 않는다 |
| d | `청년 만 19~34세` | 후보에서 **제외** |
| e | `키즈 만 12세 이하` | 후보에서 **제외** |
| f | `태블릿/웨어러블` | 후보에서 **제외** — 휴대폰 요금제가 아니다 |
| g | 제외된 것이 1건 이상 | `missingInputs` 에 `ageLimit` 안내 1건. 결과는 **200**, 남은 후보로 계산은 끝까지 간다 |
| h | 제외된 것이 0건 | `ageLimit` 안내를 넣지 않는다 — 없는 선택지를 안내하면 소음이다 |

**나이를 입력받아 판정하지 않는 이유**: 요청 스키마에 나이를 더하는 것은 `architecture.md` §3
계약 변경이라 사람 승인이 필요하다(별도 제안). 승인 전까지는 제외하고 안내만 한다 —
`청년`(18종)처럼 구간 표기가 없는 값은 나이를 받아도 판정할 수 없으므로, 업계 관행으로
"만 34세 이하"를 **지어내지 않는다**.

g 가 200 인 이유: 모르면 막지 않는다(절대 원칙 5-①). 자격을 확인할 방법이 없어도 결과는 보여준다.

## G-19. 스마트초이스가 아는 요금제 중 우리에게 없는 것을 결손으로 남긴다 (D-31)

**검증**: `SmartChoiceMissingPlanTest`

공식 API 는 `AGE = 20` 으로 스윕하므로 청년 요금제를 이미 받아온다 — KT Y덤 11종, SKT 라이트(청년),

**Y덤 11종이 전부 빠져 있었다**(원본 `KT 베이직21GB` 는 있는데 변형 `KT 베이직21GB Y덤` 이 없다).

스냅샷은 여전히 카탈로그 원본이 아니다(D-20 유지). 여기서 만드는 것은 **수집 우선순위 목록**이고,
카탈로그 진입은 사람이 CSV 에 반영할 때뿐이다(D-18 절차 그대로).

| 케이스 | 상황 | 기대 |
|---|---|---|
| a | 스냅샷에 있고 카탈로그에 없다 | `catalog_candidate` 에 `MOBILE_PLAN` · `"<통신사> <요금제명>"` 로 1행 |
| b | 스냅샷에 있고 카탈로그에도 있다 | 기록하지 않는다 |
| c | 표기만 다르다 (`KT 베이직21GB` / `kt 베이직 21GB`) | 같은 것으로 보고 기록하지 않는다 — 공백·대소문자 무시 |
| d | 배치가 여러 번 돈다 | 행이 늘지 않고 **`requested_cnt` 도 오르지 않는다** |
| e | 상한(`MAX_ROWS`)에 닿았다 | 기록만 멈추고 스윕은 끝까지 간다 |
| f | 기록이 실패한다 | 스냅샷 저장은 유지된다 (fail-soft) |

**d 가 핵심이다.** `requested_cnt` 는 "사용자가 몇 번 찾았나"이고 그것이 수집 우선순위다.
하루 3회 배치가 이 값을 올리면 아무도 찾지 않은 요금제가 우선순위 1위가 된다 — 배치는 `last_requested_at` 만 갱신한다.

사용자가 멀쩡한 구독을 해지한다. `pricing` 과 같은 기준(라인 90% · 분기 100%)으로 맞췄다.

**다섯 패키지 모두 라인·분기 100%**.

새 `DiscountRule`은 골든 케이스 없이 머지하지 않는다.
**케이스 명세 → 테스트 → 구현** 순서다.

## G-22. 카탈로그 원본 경로가 없을 때 (2026-09-17)

**검증**: `CatalogAdminDisabledTest`

**이것이 운영의 정상 상태다(D-37).** 레포 CSV 가 원본이라 편집 경로를 일부러 열지 않는다 —
여기서 503 이 나는 것은 설정 누락이 아니라 결정의 이행이다.
운영에는 `yogobi.catalog.combined-csv` 가 설정돼 있지 않다. 그 설정 그대로 도는 테스트가
`CatalogAdminDisabledTest` 다 — **기존 카탈로그 테스트 셋은 전부 경로를 넣고 돌아서** 이 조건을 놓쳤다.

| | 입력 | 정답 |
|---|---|---|
| a | `GET /api/v1/admin/catalog`, `GET /{dataset}` | **200.** 읽기는 클래스패스 합본 CSV 로 폴백한다 |
| b | `POST`·`PATCH`·`DELETE /api/v1/admin/catalog/…` | **503** `YGB-CAT-503` (500 아님) |
| c | b 이후 `catalog_change_request` 행 수 | **0.** 적용할 수 없는 제안을 쌓아 두지 않는다 |
| d | PENDING 제안에 `POST /requests/{id}/approve` | **503**, 그리고 제안은 **PENDING 그대로**·`decided_by` 는 NULL |

d 가 핵심이다. 가드가 `claim()` 뒤에 있으면 설정 문제로 **남의 제안이 FAILED 로 닫히고**,
경로를 채워도 그 제안은 되살릴 수 없다. 서버 설정 때문에 사용자 입력을 버리면 안 된다.

| b | 회원이 같은 요청 | `REPORT_SHOWN` +1 (리포트를 봤다). `GATE_SHOWN` 은 그대로 |
| c | 같은 날 3회 | 값은 3, **행은 1개**. 이벤트마다 쌓지 않고 날짜×종류로 합친다 |

## G-28. 가족결합 할인은 사용자가 말해 준 금액이다 (2026-09-17)

**검증**: `FamilyBundleDiscountGoldenTest` · `RecommendationApiTest`

카탈로그에 통신사별 결합 할인표가 없다. 그래서 **우리가 금액을 만들지 않고 사용자에게 받는다** —
해외 결제 구독에서 이미 쓰는 방법과 같다(D-17: 우리가 모르는 금액은 사용자가 확인한 값으로 채운다).

기준 금액은 기본료 55,000원이다.

| | 입력 | 정답 |
|---|---|---|
| a | 결합 O · 할인 11,000 · 3회선 | 55,000 − 11,000 = **44,000**. `CostLine` "가족결합 할인" `−11,000` · `USER_PROVIDED` |
| b | 결합 O · 할인액 없음 | **55,000 그대로.** 지어내지 않는다. `missingInputs` 에 할인액을 묻는 항목이 남는다 |
| c | 결합 X · 할인 11,000 | **55,000 그대로.** 결합 중이 아니라면 보낸 금액은 무시한다 |
| d | 결합 O · 할인 60,000 (기본료보다 큼) | **0원.** 음수 요금은 만들지 않는다. 남은 금액만큼만 깎는다 |

| f | 결합 O · 3회선만 · 할인액 없음 | **55,000 그대로.** 회선 수는 근거 문구에만 쓰고 금액에 넣지 않는다 |
| g | 할인액 음수 | **400** (`YGB-REQ-001`, field `familyBundleDiscountKrw`) |

**e 가 핵심이다.** 순서를 뒤집으면 값이 달라진다 — (55,000 − 11,000) × 0.75 = 33,000 이다.
`docs/domain.md §4` 가 선택약정 200 · 결합 300 으로 고정해 둔 이유가 이것이고, 이 케이스가 그 순서를 지킨다.

**d 를 반올림이 아니라 하한으로 적는 이유**: 결합 할인은 보통 여러 회선에 나눠 붙는데 사용자는 가구 전체

**회선 수를 왜 받고 금액에 안 쓰나**: 회선 수로 할인액을 역산하려면 통신사별 표가 필요한데 그게 없다.
받는 이유는 근거 문구("3회선 결합 기준")와, 표가 들어오는 날 사용자 입력과 대조할 값이 필요해서다.
없다고 적는 것도 정답이다 — 지금 금액에 쓰지 않는다는 뜻이다.

## G-29. 가족결합 할인은 지금 통신사에서만 유지된다 (2026-09-17)

**검증**: `RecommendationApiTest`

G-28 로 결합 할인을 받기 시작했더니 **그 금액을 모든 후보에서 똑같이 빼고 있었다.** 운영 화면에
"KCT(티플러스) 5G 티플 10GB — 가족결합 할인 −8,990원" 이 찍혔다. 알뜰폰에는 가족결합이 없고,
있더라도 통신사를 옮기는 순간 결합은 풀린다. **없어질 할인을 빼고 1등으로 올린 것**이라
사용자는 그 요금제로 갈아탄 뒤에 8,990원을 더 내게 된다 — 미사용 혜택은 0원(절대 원칙 1)의 위반이다.

결합 할인은 **통신사에 붙어 있다.** 지금 쓰는 통신사의 요금제로 바꾸면 유지되고, 다른 통신사로
옮기면 사라진다. 그래서 후보마다 "이 요금제가 지금 통신사인가"를 보고 적용 여부를 정한다.

현재 통신사는 `currentPlanId` 의 통신사 > `currentCarrier` 순으로 정한다. 요금제를 골랐다면 그 통신사가
확실하고, 이름만 적었다면 그 이름을 쓴다. 이름 비교는 `carrierExists` 와 같은 규칙이다(공백·대소문자 무시).

기준: 후보는 SKT 넷플플랜 55,000(넷플릭스 무료) · KT 웨이브플랜 45,000. 원하는 서비스는 넷플릭스,
할인액은 11,000원.

| | 입력 | 정답 |
|---|---|---|
| a | 현재 SKT · 결합 O · 11,000 | 넷플플랜 **44,000** (55,000 − 11,000) · 웨이브플랜 **58,500** (그대로) |
| b | 현재 KT · 결합 O · 11,000 | 웨이브플랜 **47,500** 이 1순위. 넷플플랜은 55,000 — **순위가 뒤집힌다** |
| c | 현재 통신사 없음(또는 "알뜰폰" 같은 분류) · 결합 O · 11,000 | 어디에도 적용하지 않는다(55,000 / 58,500) + 통신사를 묻는 안내 |
| d | 현재 `KT 엠모바일` vs 카탈로그 `KT엠모바일` | 같은 통신사로 본다 |
| e | a 처럼 적용됐고 다른 통신사 후보가 결과에 있음 | `missingInputs` 에 "다른 통신사로 옮기면 결합이 풀린다"는 안내 |
| f | `currentPlanId` 만 보냄(`currentCarrier` 없음) | 그 요금제의 통신사를 현재 통신사로 본다 — a 와 같은 결과 |

**b 가 핵심이다.** 결합 할인은 순위를 바꾼다. 모든 후보에서 똑같이 빼면 순위가 안 바뀌므로 버그가
보이지 않는다 — 한쪽에만 붙어야 이 케이스가 실패한다.

**c 를 "모르면 적용 안 함"으로 적는 이유**: 어느 통신사에 붙은 할인인지 모르면 어느 후보가 유지하는지도
모른다. 전부에 빼면 전부가 8,990원씩 싸 보이고, 그중 하나는 거짓이다. 지어내지 않는다(D-17).

## G-30. 현재 요금제를 알려주면 같은 기준으로 계산한다 (2026-09-17)

**검증**: `RecommendationApiTest`

지금까지 결과 표의 '현재' 열은 **사용자가 적어 준 통신비 + 구독 정가의 합**이었다. 화면의 메모였고
BE 는 그 값을 본 적이 없다. 그 옆의 '추천' 열은 할인을 반영한 실질월비용이라 **두 열의 기준이 달랐다** —
82,284원과 49,690원을 나란히 놓고 "32,594원 절약"으로 읽히지만 실제 절감액은 8,990원이었다.

`optional.currentPlanId` 로 지금 쓰는 요금제를 받으면, **후보와 똑같은 계산기·똑같은 컨텍스트**로
그 요금제의 실질월비용을 내어 `current` 에 싣는다. 같은 구독을 유지한다고 보고 계산하므로
비교 가능한 두 금액이 된다.

| | 입력 | 정답 |
|---|---|---|
| a | `currentPlanId` = 웨이브플랜(45,000) · 넷플릭스 희망 | `current.cost.monthlyTotal` = **58,500** (45,000 + 넷플릭스 13,500) |

## G-48. 구독 공식가는 출처가 같을 때만, 1원 차이도 제안한다 (2026-09-20, D-60)

**검증**: `SubscriptionHarvestTest`

내레이터 레포의 `POST /operations/subscriptions/check` 가 공식 페이지를 읽어 **원문을 인용**해 준다.
저쪽은 계산도 저장도 하지 않는다 — 대조·제안·승인·반영은 전부 BE 다(D-18·D-28·D-43 이 그대로 산다).

| | 상황 | 정답 |
|---|---|---|
| a | 공식가 8,691 · 카탈로그 8,690 | **제안 1건.** 허용 오차 **0** — 요금제의 100원과 다르다 |
| b | 공식가 = 카탈로그 | 제안 없음 |
| c | `sourceUrl` ≠ 우리 `official_url` | **그 서비스 통째로 건너뜀** + `SUBSCRIPTION_SOURCE_DRIFT` 기록 |
| d | 조회 실패(`CATALOG-SOURCE-CHANGED` 등) | 제안 없음 + `SUBSCRIPTION_CHECK_FAILED` 에 **코드 그대로** 기록 |

**URL 드리프트 가드가 필요한 이유**: 저쪽은 SSRF 때문에 요청으로 URL 을 받지 않아 주소를 자기 레포에 둔다.
같은 URL 이 두 곳에 따로 사는 구조라, 우리가 카탈로그에서 주소를 고치면 저쪽은 옛 페이지를 계속 읽는다.
그때 **엉뚱한 페이지의 가격이 제안으로 올라온다** — 조용한 실패 중 가장 나쁜 종류다.

## G-51. '변경 최소'가 '지금'보다 비싸면 지금 요금제가 조건 미달이다 (2026-09-20, 통합 점검)

|---|---|---|

| b | 같은 서비스 중앙값의 **10배 초과** | 이름에 표기가 없는 건(교보 북모닝 282,000)을 잡는다 |
| c | 메모에만 기간 표기가 있는 등급 | **걸리면 안 된다** |

넷을 전부 잡으면서 운영 카탈로그 130건에 **오탐 0** 이다(2026-09-20 실측).

**빼기로 한 신호 둘을 적어 둔다 — 같은 실수를 두 번 하지 않도록.**

| 뺀 신호 | 왜 |
|---|---|
| **다른 등급 가격의 정수배** | 스토리지 등급이 서로 정수배인 게 흔하다(iCloud+ 88,000 = 44,000 × 2). **9건** |
| **메모의 기간 표기** | 메모는 우리가 쓰는 설명문이라 기간 낱말이 늘 섞인다 — "1개월 정기 구독"(PS Plus 셋) · "멤버 1인당 1개월"(Notion 둘) · "연간 요금제 별도 존재"(Gemini) · **선불권을 왜 안 실었는지 적어 둔 문장**(지니뮤직). **7건 전부 오탐** |

둘 다 "상시 주황" 을 만든다. **카드가 늘 켜져 있으면 진짜 한 건이 섞여도 안 보인다.**


## G-55. 스마트초이스가 확인한 청년 파생형 결손은 검수를 거쳐 원본에 들어간다 (2026-09-20)

`requestedSktYouthPlanUsesItsOfficialBaseRowAndRoundsDecimalGb`, `unparseableYouthPlanRemainsARequestedGap`)

스위프는 KT Y덤을 이미 받아 `catalog_candidate`에 남기지만, 이 표는 수집 우선순위일 뿐이라
검수함과 연결되지 않았다. 스마트초이스를 원본으로 바꾸지 않고, **공식 기본 행과 이름으로
대응되는 KT `Y덤`·SKT `(청년)` 파생형만** 기존 제안·승인 경로에 올린다.

| | 상황 | 정답 |
|---|---|---|
| a | `베이직21GB Y덤` 결손 + 스냅숏 `42GB` | `CREATE` 제안·`VERIFIED`, `data_mb=43008`, `age_limit=청년` |
| b | 제안 직후 | 결손만 `PENDING`; **CSV·DB는 불변** |

| d | SKT `(청년)` + `1.4GB` | 기본 행을 재사용하고 `data_mb=1434`로 반올림 |
| e | 기본 행이 없거나 데이터 표기를 안전하게 MB로 바꿀 수 없음 | 제안하지 않고 결손으로 남김 |

음성·문자·망·공식 URL은 각 통신사의 공식 기본 행을 재사용한다. 금액·총 데이터는 정확한 이름의
스마트초이스 스냅숏에서만 읽는다. 이 대응이 없는 다른 결손까지 자동 승격하지 않는다.

## G-56. 퍼널의 "사람 수"는 사람 수여야 한다 — 전환율은 행위자 교집합으로 낸다 (2026-09-21)

**검증**: `FunnelCounterTest` (`g56a_uniqueCountsPeopleNotPersonDays`,
`g56b_conversionCountsActorsPresentInBothStages`, `g56c_unmeasurableRatesAreNullNotZero`)

`funnel.unique`는 "사람 수"라는 이름으로 나가는데 실제로는 **일별 사람 수를 14일 더한 값**이었다.
사흘 들른 한 사람이 3 으로 세어진다 — 사람-일이지 사람이 아니다. 백오피스가 이 값을 막대로 그리려
했고(프론트 세션, 2026-09-21), 그리면 라벨이 거짓이 된다. `actor_key`로 묶어 창 전체에서 한 번만 센다.

전환율도 같은 이유로 **두 합계의 나눗셈이 아니다.** 같은 행위자가 두 단계를 다 밟았는지로 낸다.

| | 상황 | 정답 |
|---|---|---|
| a | `u:1`이 REPORT_SHOWN 을 사흘(0·1·2일 전) | `unique.reportShown = 1` |
| b | `u:1` 로그인+리포트+저장(다른 날), `u:2` 로그인만 | `loginToReport = 50.0`, `reportToSaved = 100.0` |
| c | 아무도 리포트를 안 봄 | `reportToCalendar = null` — 0.0 이 아니다 |
| d | 게이트(`ip:`)와 로그인(`u:`) | `gateToLogin = null`, 키는 존재한다 |

**d 가 핵심이다.** 비회원은 `ip:` 키, 회원은 `u:` 키라 같은 사람을 이을 방법이 없다. 둘을 나누면
전환율처럼 보이지만 서로 다른 모집단이고, 회원이 많은 날은 100%를 넘는다. 못 내는 비율은 **키를
지우지 말고 null 로 낸다** — 키가 없으면 화면이 "아직 안 만들었나"로 읽고, 0 이면 "다 이탈했다"로 읽는다.
`gateDropEstimate`가 이 한계에 붙인 이름이고 그 이름은 그대로 둔다.

## G-57. 화면만 아는 단계는 받되 서버가 보는 단계는 받지 않는다 — 그리고 모든 단계가 실제로 쌓인다 (2026-09-21)

**검증**: `FunnelCounterTest` (`g57a_clientReportedStageIsRecorded`,
`g57b_serverObservedStagesAreNotAcceptedFromTheClient`, `g57c_unknownKindIsDroppedWithoutAnError`,
`g57d_savingOpportunityRateUsesTheReportThreshold`, `g57e_unavailableKpisCarryTheirReason`,
`g57f_everyKindActuallyLandsInBothTables`)

보고서 §9.2 "결과 도달률"의 분모는 **입력 시작 사용자**인데 입력은 전부 브라우저 안에서 끝나
서버에 아무 요청도 오지 않는다. `POST /api/v1/events`로 화면이 알려 준다.

| | 상황 | 정답 |
|---|---|---|
| a | `{"kind":"INPUT_STARTED"}` | 204, 두 표에 1건 |
| b | `{"kind":"REPORT_SHOWN"}` 등 서버 관측 5종 | 204, **0건** — 거절도 하지 않는다 |
| c | 모르는 종류·빈 본문 | 204, 0건 |
| d | 절감 9,000 / 5,000 / 4,999원 세 회원 | `savingOpportunityRate = 66.7`, 기준 5,000원은 **포함** |
| e | 아직 못 내는 KPI | 키는 있고 값은 `null`, `*Note` 에 이유 |
| f | `FunnelCounter` 의 모든 종류 | 전부 `funnel_daily`·`funnel_event` 양쪽에 쌓인다 |
| g | 한 번도 안 쌓인 종류 | `funnel.lastSeen` 에 **키는 있고 값이 `null`** — 목록에서 사라지지 않는다 |

**b 가 보안 조건이다.** 서버가 스스로 관측하는 단계를 화면이 보낼 수 있게 하면 요청 한 번으로
리포트 조회 수를 부풀릴 수 있고, 그러면 퍼널 전체가 증거로서 죽는다. 공개 경로가 받는 집합은
`FunnelCounter.CLIENT_REPORTED` 뿐이다.

**f 는 이미 새어 나간 사고를 막는 그물이다.** `funnel_daily.kind` 의 CHECK 가 D-36 당시의 세 종류만
허용하는데 D-52 에서 `CALENDAR_SHOWN`·`RESULT_SAVED` 를 부르기 시작했다. 집계 실패는 삼켜지므로
(기능이 지표 때문에 멈추면 안 된다) WARN 한 줄만 남고, **두 단계가 2026-09-18 부터 한 건도 안 쌓였다.**
화면에서는 "아직 아무도 안 했다"와 구분되지 않았다. V31 이 종류를 넓혔고, 이 테스트는 상수를
**반사로 훑어** 새 단계를 추가해도 목록을 고치지 않고 걸리게 한다 — 하나 고치고 끝내지 않기 위해서다.

**g 는 같은 사고를 눈으로 잡는 장치다**(프론트 세션 제안, 2026-09-21). 표를 `GROUP BY` 로만 읽으면
행이 없는 종류는 결과에 아예 안 나오고 "아무도 안 했다"와 구분되지 않는다. `FunnelCounter.ALL` 을
기준으로 좌외부조인해 **행이 없는 것 자체가 화면에 뜨게** 한다.

## G-58. 놓친 단계는 남아 있는 기록에서만 되살린다 (2026-09-21)

**검증**: `FunnelCounterTest` (`g58a_missedSavesAreRestoredFromTheRowsThatRemain`,
`g58b_todayIsLeftToLiveCountingInTheCountTable`, `g58c_stagesWithoutEvidenceAreNotInvented`)

V31 이 CHECK 를 넓혀도 2026-09-18~21 에 안 쌓인 값은 돌아오지 않는다. `FunnelBackfill` 이
되살릴 수 있는 것만 되살린다.

| | 상황 | 정답 |
|---|---|---|
| a | 같은 회원이 3일 전에 두 번, 다른 회원이 3일 전 한 번, 첫 회원이 2일 전 한 번 저장 | 사람-일 3건. 일별 횟수는 3일 전 `3`·2일 전 `1` |

| b | 오늘 저장한 건 | `funnel_event` 에는 들어가고 **`funnel_daily` 에는 안 들어간다** |

그 시절에 존재하지 않던 신호다. **다른 값으로 대신 세우면 그 순간 퍼널이 증거이기를 그만둔다.**

**b 는 두 번 세지 않기 위한 경계다.** `funnel_event` 는 (날짜·종류·행위자)가 기본키라 오늘까지
넣어도 중복이 안 생기지만, `funnel_daily` 는 횟수를 누적하므로 오늘은 실시간 집계가 주인이다.

## G-59. 결과 도달률은 비회원·회원 두 경로를 모두 이어서 센다 (2026-09-21)

**검증**: `FunnelCounterTest` (`g59a_resultReachRateJoinsBothTheGuestAndMemberPaths`,
`g59b_withoutAnyInputTheRateIsNullWithItsReason`)

보고서 §9.2 "결과 도달률". 분모는 **입력 시작 사용자**, 분자는 그중 결과 화면까지 간 사람이다.
두 합계의 나눗셈이 아니라 같은 행위자가 두 단계를 다 밟았는지로 센다(G-56 과 같은 규칙).

| | 상황 | 정답 |
|---|---|---|
| a | 비회원 입력→게이트, 회원 입력→리포트(다른 날), 입력만 하고 떠난 사람 | `resultReachRate = 66.7`, `resultReachOf = 3` |
| a' | 값이 있을 때 | `resultReachRateNote` 를 **달지 않는다** |
| b | 입력 시작이 0건 | `null` + 이유. `resultReachOf = 0` |

**a 가 이 케이스의 이유다.** 도달은 두 모양이다 — 비회원은 게이트(`ip:` 키), 회원은 리포트(`u:` 키).
`INPUT_STARTED` 도 같은 규칙으로 찍히므로 양쪽 다 이어진다. 익명으로 시작해 중간에 로그인한
사람은 게이트를 먼저 밟으므로 분자에 든다. **한쪽 경로만 세면** 회원이 많은 날과 비회원이 많은
날의 값이 서로 다른 뜻이 되어 추이로 읽을 수 없다.

`gateToLogin`(G-56 d)은 여전히 못 낸다. 거기는 두 단계의 키 체계가 서로 다르지만, 여기는
입력 시작과 도달이 **같은 행위자 키**로 찍히므로 이을 수 있다.

## G-60. 날짜를 자르는 기준은 한국시간이다 (2026-09-21)

**검증**: `FunnelCounterTest` (`g60_dayBoundariesFollowKoreanTime`)

서버는 UTC 로 돈다. 그대로 두면 `CURRENT_DATE` 가 UTC 날짜라 **KST 00:00~09:00 의 활동이
전날로 찍힌다** — 국내 서비스의 "오늘 몇 명"이 9시간 어긋난다. 프론트 세션이 대시보드에서
발견했다(2026-09-21).

| | 상황 | 정답 |
|---|---|---|
| a | DB 세션 시간대 | `Asia/Seoul` |
| b | `SELECT CURRENT_DATE` | 한국시간 기준 오늘 |
| c | 퍼널 기록 후 `funnel_daily.day` | 한국시간 기준 오늘 |
| d | `funnel.dateBasis` | `"Asia/Seoul"` — **박아 넣지 않고 세션에서 읽는다** |

**c 가 있는 이유**: 집계만 고치고 쓰기 경로가 UTC 면 둘이 어긋난다. 같은 기준을 써야 한다.

**d 가 있는 이유**(프론트 세션 요청): 화면이 "UTC 기준"을 박아 두면 이 변경이 배포되는 순간
거짓이 되고, 두 레포가 같은 분에 손을 맞춰야만 맞는 문구가 된다. 기준을 응답에서 읽게 하면
BE 배포만으로 문구가 따라온다. 서버도 상수로 박지 않고 **세션에서 실제 값을 읽어** 내보낸다 —
설정과 응답이 어긋날 수 있는 틈을 두지 않는다.

고치는 지점은 `application.properties` 의 `spring.datasource.hikari.connection-init-sql` **한 줄**이다.
쿼리마다 `AT TIME ZONE` 을 흩뿌리면 **새로 쓰는 쿼리가 반드시 빠뜨린다.** a 단언이 그 유일한
지점을 고정한다 — b·c 만 있으면 UTC 로 돌아가도 하루의 3분의 2 는 우연히 통과한다.

**저장값은 바뀌지 않는다.** 전부 `TIMESTAMPTZ`(절대 시각)이고, 바뀌는 것은 날짜를 어디서
자르느냐다. 다만 이 변경 이전에 쌓인 `DATE` 열(`funnel_daily`·`funnel_event`·`recommendation_daily`)은
UTC 기준으로 들어가 있어 **2026-09-21 에 9시간짜리 이음매가 있다.** 그 전 구간을 KST 로
소급 보정하지 않았다 — 원본에 시각이 남지 않은 집계 행이라 되돌릴 근거가 없다.

`@Scheduled` 는 원래부터 전부 `zone = "Asia/Seoul"` 이었고, 자바 쪽 날짜도 `PrivacyPolicy.RETENTION_ZONE`
을 명시해 쓴다 — `ZoneId.systemDefault()` 는 어디에도 없다. 이 변경으로 어긋날 곳이 없는 이유다.

## G-61. 계산 내역의 등급 이름은 서비스까지 말한다 (2026-09-21)

d 가 필요한 이유: 대표 등급 선택이 이름에 "스탠다드"·"광고"가 들어 있는지로 판정한다. 접두가 그
판정을 깨지 않는지 고정한다(서비스명에 그 낱말이 없음을 확인했다).

**e 는 첫 규칙의 구멍이었다**(내레이터 세션이 운영 문장에서 찾았다, 2026-09-21). 전체 포함만 보면
**낱말만 겹치는 경우**를 놓친다 — 운영 설명에 `"카카오 이모티콘 플러스 이모티콘 플러스" 구독을…`
이 나갔다. 규칙을 넷으로 늘렸다.

| 서비스 + 등급 | 결과 | 왜 |
|---|---|---|
| 유튜브 프리미엄 + 유튜브 프리미엄 라이트 | `유튜브 프리미엄 라이트` | 등급명이 서비스명을 통째로 품는다 |
| YouTube Music + Music Premium 개인 | `YouTube Music Premium 개인` | 끝과 앞이 겹치면 접는다 |
| 카카오 이모티콘 플러스 + 이모티콘 플러스 | `카카오 이모티콘 플러스` | 겹친 부분이 등급명 전부다 |
| Google One + Google AI Plus 2TB | `Google AI Plus 2TB` | 등급명이 이미 브랜드를 말한다 |
| 넷플릭스 + 스탠다드 | `넷플릭스 스탠다드` | 나머지는 앞에 붙인다 |

**내레이터가 문구를 안 다듬은 것이 옳다.** 거기서 손대면 그게 곧 라벨 문자열 매칭이고, 그 순간
"BE 가 준 값을 그대로 옮긴다"는 경계가 무너진다. 판정은 값을 만드는 쪽에 있어야 한다.

규칙이 자바에 있으므로 f 는 **SQL 로 흉내 내지 않고 같은 메서드를 돌려** 확인한다 — 사본을 만들면
둘이 어긋나는 날이 온다(D-61 ③ 과 같은 이유).

## G-62. 공개 절감액 통계는 표본 수를 내보내지 않는다 (2026-09-21)

**검증**: `SavingsStatsApiTest` (`belowThresholdExposesNothing`, `aboveThresholdExposesAmountsOnlyOnePerAccount`)

D-59 는 **화면에** 표본 수를 적지 않기로 했다 — "이용자 2명 기준"은 평균이라는 이름으로 두 사람의
금액을 거의 그대로 알려 주는 셈이라서다. 그런데 **그 방어가 화면에만 있었다.** 공개 경로라
인증 없이 받으면 `sampleCount` 와 개인별 금액 배열이 그대로 나왔다.

| | 상황 | 정답 |
|---|---|---|
| a | 임계값 미만 | `samples: []`, `sampleCount` **키 자체가 없다** |
| b | 임계값 이상 | 금액·평균·중앙값만. 응답 본문에 `sampleCount` 문자열이 없다 |

**남는 한계를 같이 적는다.** `samples` 자체가 개인별 절감액이고 길이를 세면 표본 수가 그대로 나온다.
줄어든 것은 노출 표면이지 노출 자체가 아니다 — 랜딩이 그 금액들을 돌려 보여 주는 게 기능이라
지금 구조에서는 여기까지다. 더 줄이려면 금액을 구간으로 뭉개거나 요청마다 하나씩만 주는 설계가
필요하고, 그건 화면 기획과 같이 정한다(발표 뒤 과제, 프론트 세션과 합의).

**교훈**: 정책을 화면에서 지키면 API 는 안 지킨다. D-59 같은 결정은 **응답을 만드는 자리**에 둬야 한다.

## G-63. 유튜브 프리미엄은 YouTube Music 을 포함한다 (2026-09-21, 사용자 승인)

**검증**: `YouTubePremiumOverlapTest` (`g63a`~`g63e`)

카탈로그가 **실제와 정반대로** 적혀 있었다 — 8,500원 라이트에 "YouTube Music 앱 포함",
14,900원 프리미엄에 "YouTube Music 앱 제외". 게다가 같은 상품이 이름만 다르게 두 행이었다
(`유튜브 프리미엄 라이트` id 16 / `Premium Lite` id 19, 둘 다 8,500원).

**돈이 틀렸다.** 메모만 고치면 계산은 그대로다 — 계산기는 고른 등급의 금액을 더할 뿐이다.
운영에서 유튜브 프리미엄 + YouTube Music 을 고르면 `14,900 + 11,990 = 26,890원` 이 나왔다.
실제로는 14,900원이 끝이고 **월 11,990원을 과다 계산**하고 있었다. "겹치는 구독을 찾아준다"는
서비스가 정작 **자기 카탈로그의 겹침을 못 보고 있었다.**

| | 상황 | 정답 |
|---|---|---|
| a | 프리미엄 + Music 둘 다 원함 | 번들 하나(14,900원)로 접힌다 |
| b | 하나만 원함 | 번들이 안 붙는다 — 음악만 듣는 사람에게 영상 요금을 물리면 그게 새 거짓말이다 |
| c | 프리미엄 메모 | "YouTube Music 포함" — "제외"가 아니다 |
| d | 8,500원 등급 | **하나뿐**. 남긴 쪽은 공식 표기에 가깝고 설명도 정확한 id 19 |
| e | 중복이던 id 16 | 어디서도 활성이 아니다 |

**고친 방법은 번들이다.** 기존 기계를 그대로 쓴다 — 구성 등급을 전부 원할 때만 적용되고,
하나만 원하면 각각 제 가격으로 나간다. 새 규칙을 만들지 않았다.

**e 가 `active = false` 가 아니라 "활성 아님"인 이유**: 새 DB 에서는 id 16 이 애초에 안 들어가
행이 없고, 이미 있던 DB(운영)에서는 비활성으로 내려간다(G-53). 두 경우를 한 단언으로 덮는다 —
`active = false` 로 못박으면 새 DB 에서 거짓 실패가 난다. 지우지 않고 내리는 이유는 예전에
id 16 으로 저장한 결과가 계속 읽혀야 하기 때문이다.

**1차 출처(D-43)**: Google 공식 YouTube 고객센터
`https://support.google.com/youtube/answer/6308116?hl=ko` — *"YouTube Premium 혜택의 일환으로
YouTube Music 앱에서 광고로 끊김 없이 오프라인으로 이동 중에도 음악을 즐길 수 있습니다."*
가격 8,500 / 14,900 은 유튜브 공식 블로그 `https://blog.youtube/intl/ko-kr/news-and-events/yt-premium-lite-kr/`.
확인일 2026-09-21. **라이트가 Music 을 제외한다는 문장은 1차 출처에서 직접 못 읽었다** —
id 19 의 기존 메모와 상품 구조상 맞지만, 확인했다고 적지 않는다.

## G-63 후기. 퇴역한 행의 이름은 다시 쓸 수 없다 — 운영 5분 중단 (2026-09-21)

**아직 검증자가 없다 — 발표 후 과제.** 여기 적는 이유는 같은 함정을 또 밟지 않기 위해서다.

G-63 ②로 중복 등급 id 16 을 합본에서 내린 뒤, 살아남은 id 19 의 이름을 공식 표기
`유튜브 프리미엄 라이트` 로 바꿨다. **운영이 기동에 실패하며 죽었다.**

```
duplicate key value violates unique constraint "subscription_tier_service_id_name_key"
Detail: Key (service_id, name)=(6, 유튜브 프리미엄 라이트) already exists.
```

`subscription_tier` 에 `(service_id, name)` 유니크 제약이 있고, **비활성 행도 그 이름을 계속 점유한다.**
G-53 은 퇴역 행을 지우지 않고 `active = FALSE` 로만 내리므로(예전 저장 결과가 계속 읽혀야 한다),
운영에는 id 16 이 그 이름 그대로 남아 있었다. 시드 로더가 id 19 를 같은 이름으로 바꾸려다 충돌했다.

**테스트는 전부 통과했다.** 새 DB 에는 id 16 이 애초에 안 들어가기 때문이다 — CSV 에서 지운 행은
테스트 DB 에 존재한 적이 없다. **퇴역 행은 운영에만 있는 상태이고, 테스트가 그 모양을 갖지 않는다.**
G-61 이 "테스트 데이터가 실제 데이터를 안 닮으면 통과하면서 틀린다"고 적은 것과 같은 함정을,
그걸 적은 날 다시 밟았다.

**되돌렸다.** 이름은 `Premium Lite` 그대로이고 계산 내역 라벨은 "유튜브 프리미엄 Premium Lite" 다.
중복 제거·메모 정정·겹침 번들(G-63 a~e)은 그대로 살아 있다 — 돈은 맞다.

**제대로 고치려면** 퇴역 시 이름을 놓아주는 절차가 있어야 한다(마이그레이션으로 비활성 행의 이름에
표식을 붙이거나, 퇴역 단계가 그렇게 하도록). 그러면 예전 저장 결과가 보는 라벨이 달라지므로
화면과 같이 정할 문제다. **이름 재사용 자체가 지금 구조에서는 안전하지 않다**는 것이 결론이다.

## G-64. 망을 좁혀서 더 싼 요금제를 놓쳤으면 그 사실을 말한다 (2026-09-21, 사용자 사례)

**검증**: `RecommendationApiTest` (`g64_narrowingTheNetworkSaysWhatItCost`)

실제 사용자 결과에서 나왔다. KT 요고 49(120GB) 사용자가 **무제한**을 원하며 디테일 모드에서
"사용 중인 통신망"에 5G라고 사실대로 답했더니 **"지금 요금제가 더 싸요"**가 나왔다.

| 조건 | 1순위 | 절감액 |
|---|---|---|
| 망 미지정 | 이지모바일 59,700원 | **+2,800원** |
| 5G 로 좁힘 | KT엠모바일 68,500원 | **−6,000원** |

**계산은 맞았다. 질문이 틀렸다.** 화면은 "**사용 중인** 통신망"을 묻고 BE 는 그 답을 후보 필터로
쓴다 — 그런데 **"지금 5G를 쓴다"와 "5G만 원한다"는 다른 말이다.** 알뜰폰 무제한은 대부분 LTE라,
사실대로 답한 한 번이 월 8,800원을 지웠다. **화면 어디에도 그 사실이 없었다.**

| | 상황 | 정답 |
|---|---|---|
| a | 5G 로 좁혔고 LTE 쪽이 더 쌈 | 뺀 건수와 기본료 차액을 말한다. 문구는 `5G` — 내부 enum `FIVE_G` 가 아니다 |
| b | 망을 안 고름 | "뺐어요" 안내를 넣지 않는다(다른 안내는 원래 나간다) |
| c | 좁혔는데 뺀 쪽이 더 비쌈 | 말하지 않는다 — 손해가 아니다 |

**필터는 없애지 않았다.** 사용자가 고른 조건이다. 대신 그 선택이 무엇을 지웠는지 숫자로 말한다.
**총액은 약속하지 않는다** — 비교는 기본료끼리이고 제휴 혜택은 후보마다 달라 뒤집힐 수 있다.

a 의 `FIVE_G` 단언이 있는 이유: 처음 붙였을 때 안내 문구에 내부 enum 이 그대로 나갔다.
사용자는 그 낱말을 모른다.

**후속(화면)**: 질문을 "**희망하는** 통신 규격 — 5G / 상관없어요"로 바꾸기로 했다(사용자 결정,
라이트·디테일 모두). 그러면 이 안내는 5G를 고른 사람에게만 남는다.

## G-66. 기간 한정 특가는 모르면 모른다고 답한다 (2026-09-21, 사용자 지시)

**검증**: `RecommendationApiTest` (`g66_aPromotionalPlanDoesNotPretendToKnowThePeriodTotal`)

알뜰폰은 3·6·7개월 특가가 흔한데 **카탈로그에 그 기간을 담을 칸이 없었다** — `mobile_plan` 에는
`base_price` 와 약정할인 12/24개월뿐이었다. 그래서 같은 표에 두 가지가 섞여 있었다.

| 이름 | 저장된 `base_price` | 실제 |
|---|---|---|
| 이지모바일 `[무제한]7개월 특가 매일5GB+5Mbps` | 46,200원 | **특가가**. 7개월 뒤 복귀가 없다 |
| 큰사람커넥트 `[SK] 12개월간 10원! 저렴한 장기할인` | 27,500원 | **정상가**. 특가 10원이 없다 |
| 큰사람커넥트 `[12개월간 990원 특가] 4.5기가` | 31,900원 | 정상가. 특가 990원이 없다 |

운영 1,706건 중 **13건**. `annualSavings = monthlySavings × 12` 라 **그 요금제들에서 연 절감액이
틀렸고**, 화면의 6·12개월 토글도 같은 값을 썼다. 사용자가 실제 결과에서 찾았다.

**V32** 가 `promo_months`·`regular_price` 를 더했다. `base_price` 의 뜻은 바꾸지 않았다 —
지금(1개월차) 내는 금액이고, 기존 계산·정렬이 전부 이 값을 쓰므로 의미를 바꾸면 순위가 흔들린다.

| | 상황 | 정답 |
|---|---|---|
| a | 7개월 특가, 종료 후 금액 **모름** | 6개월 절감액은 **숫자**, 12개월은 **`null`**. 기간마다 따로 판정한다 |
| b | 7개월 특가, 종료 후 30,000원 | 기간 값을 낸다. 안내가 그 금액을 적는다 |
| c' | 바뀐 뒤 금액이 **지금과 같음** | 값은 싣되 **말은 하지 않는다** |
| c | 특가 아님 | 아무 말도 하지 않고 기간 값도 그대로 |

**c' 가 필요한 이유**(프론트 세션 지적, 2026-09-21): 13건 중 **8건이 X = Y** 다. 그 행들에
안내를 내면 `지금도 46,200원인데 7개월 뒤 46,200원으로 바뀌어요` 가 된다 — 읽는 사람은 뭔가
바뀐다고 믿는다. **안 바뀌는데 바뀐다고 적는 것도 틀린 말이다.** 행은 그대로 둔다:
"확인했고 안 바뀐다" 는 것도 아는 값이라 지우면 다시 확인해야 한다.

**`null` 이지 0 이 아니다.** 0 은 "안 아낀다"는 뜻이라 다른 거짓말이 된다. 추정값도 넣지 않는다(D-43).

**안내가 계산과 같은 값에서 나온다.** 처음에는 요금제 **이름**에서 "7개월"을 정규식으로 긁어
경고만 띄웠다 — 이름은 출처에서 온 문자열이라 거짓은 아니지만 **그걸로는 계산을 못 고쳤다.**
연 절감액은 여전히 월 × 12 였다. 지금은 카탈로그 값 하나를 계산과 문구가 같이 본다.

`mobile_plan_promo` 섹션은 **매번 전부 지우고 다시 쓴다.** 업서트만 하면 특가가 끝나 합본에서
행을 지워도 DB 에 영원히 남는다 — **특가는 끝나는 것이 정상**이라 G-53 보다 더 위험하다.

**기간 값은 실제로 혼합해 계산한다.** 처음 붙였을 때는 `regular_price` 를 알아도 여전히 월 × N 을
하면서 안내만 "그만큼 반영해 계산했어요" 라고 적었다 — **말한 것을 하지 않는 쪽이 모른다고 말하는
것보다 나쁘다**(2026-09-21 그룹 B 검증 중 발견). 지금은 `특가개월 × 지금월액 + 남은개월 × (지금월액
+ 차액)` 으로 낸다. 구독 금액은 그대로이므로 달라지는 것은 요금제 부분뿐이다.

**특가가 끝나면 싸지는 경우도 있다.** `7743` 은 `월 27,500원, 12개월 이후 4,800원/월` 이다 —
이름이 "장기할인" 이고 실제로 내려간다. 그래서 문구가 "특가가 끝나요" 가 아니라 "금액이 바뀌어요" 다.
부호를 가리지 않고 그대로 더한다.

**출처 페이지의 구조를 13건 전부 확인했다**(2026-09-21, 5건은 직접 열어 대조). 형식이 하나다:

```
월 {X}원  {N}개월 이후 {Y}원/월       X = 그 페이지의 "월 납부총액" = 우리 base_price
```

| 무리 | X vs Y | 뜻 | 건수 |
|---|---|---|---|
| A | X = Y | 월 요금이 안 바뀐다. "특가"가 요금이 아닌 다른 것을 가리킨다 | 8 |
| B | X > Y | **나중에 싸진다**(장기할인·약정형). 특가가 끝나는 게 아니다 | 5 |

**`base_price` 를 바꾸지 않았다.** 5건 전부 우리 값이 페이지의 `월 납부총액` 과 **정확히 일치**한다 —
바꾸면 그 페이지가 "지금 내는 돈" 이라고 말하는 숫자를 버리는 셈이다.

**상품명은 쓰지 않는다.** `[SK] 12개월간 10원!` 인데 같은 페이지의 결제 정보는 `월 납부총액 27,500원`
이고 요금 문구는 `12개월 이후 4,800원/월` 이다 — **한 페이지 안에서 세 숫자가 서로 안 맞는다.**
이름은 판매 문구이고 결제 정보가 값이다. AI 세션이 이름의 숫자를 안 실어 보낸 판단이 옳았다.

**13행 모두 `regular_price` 가 찼다**(2026-09-21). B 무리는 나중에 싸지므로 기간 절감액이 **늘어난다** —
예를 들어 7755 는 7개월 뒤 월 8,800원 싸져 12개월 절감액이 44,000원 커진다. 채우려면 특가 종료 후 금액을 1차 출처에서
확인해야 한다. 그때까지 12개월 절감액은 그 요금제들에서 `null` 이다 — 틀린 수보다 빈칸이 낫다.


## G-67. 절감 추천 알림도 끌 수 있어야 한다 (2026-09-21, 사용자 승인)

**검증**: `PrivacyApiTest` (`g67_savingsAlertConsentCanBeTurnedOffAndBackOn`,
`g67b_savingsAlertConsentIsGuardedLikeMarketing`)

`SAVINGS_ALERT` 는 로그인할 때 체크만 받고 **끄는 길이 없었다.** 처리방침 7조가 처리정지를
약속하는데 화면에도 API 에도 길이 없으면 **그 약속이 빈말**이다. 프론트 세션이 마이페이지
동의 관리를 열면서 지적했다.

| | 상황 | 정답 |
|---|---|---|
| a | 로그인 때 선택 안 함 | 행이 없다 — 기본은 미동의 |
| b | `{"agree":true}` | `{agreed:true}`, `withdrawn_at` 이 null |
| c | `{"agree":false}` | `{agreed:false}`, `withdrawn_at` 에 시각. **행은 지우지 않는다** |
| d | 다시 `true` | 되살아난다. 철회가 끝이 아니다 |
| e | CSRF 없음 / `"yes"` | 403 / 400 |

**발송 기능은 아직 없다** — 지금 남는 것은 동의 증적뿐이다. 그래도 끄는 길을 먼저 연다:
**보내기 시작한 다음에 만들면 그 사이에 받은 사람은 끌 수 없었다.**

**마케팅과 같은 모양이어야 한다.** 같은 성격의 선택 항목을 다른 모양으로 두면 화면이 둘을
다르게 다루게 되고 언젠가 한쪽만 고쳐진다. `setOptional(userId, item, agree)` 하나를 둘이 쓴다.

**철회가 행을 지우지 않는 이유**: 언제 동의했고 언제 철회했는지가 증적이다. 지우면 그 기록이 사라진다.

**e 의 비인증 POST 는 401 이 아니라 403 이다** — CSRF 필터가 인증보다 먼저 걸린다.
인증 여부는 같은 경로의 GET 으로 본다.

## G-68. 퇴역한 등급의 이름을 다시 쓸 수 있다 (2026-09-21, V33)

**검증**: `TierDisplayNameTest` (`g68_aRetiredTierDoesNotHoldItsNameHostage`,
`g68b_activeTiersStillCannotShareAName`)

`UNIQUE (service_id, name)` 이 **비활성 행에도 걸렸다.** 합본에서 사라진 행은 지우지 않고
`active=FALSE` 로만 내리므로(예전 저장 결과가 계속 읽혀야 한다, G-53), 한 번 쓰인 이름은 다시
못 썼다. 중복 등급 `id 16` 을 내리고 살아남은 `id 19` 에 그 이름을 주려다 **운영이 5분 죽었다.**

| | 상황 | 정답 |
|---|---|---|
| a | 같은 이름을 쥔 **비활성** 행이 있는데 활성 행에 그 이름을 준다 | 들어간다. 퇴역 행은 이름을 **간직하되 점유하지 않는다** |
| b | **활성끼리** 같은 이름 | 여전히 거절 — 느슨하게 한 것이지 없앤 것이 아니다 |

제약을 **활성 행에만** 건다(부분 유니크 인덱스). 뜻이 오히려 정확해진다: 지금 팔리는 등급끼리
이름이 겹치면 안 되는 것이지, 옛날 이름을 영원히 예약해 둘 이유가 없다.

**a 의 픽스처가 이 케이스의 전부다.** 전에는 테스트가 전부 통과했다 — 새 DB 에는 퇴역 행이
**존재한 적이 없기 때문**이다. 퇴역 행은 운영에만 있는 상태이고, 그 모양을 테스트가 갖지 않으면
이 종류는 영영 안 잡힌다. 그래서 여기서는 **운영의 모양을 일부러 만든다.**

이로써 G-63 d 의 이름을 공식 한국어 표기 `유튜브 프리미엄 라이트` 로 되돌렸다.

## G-69. 공개 표본은 정확한 금액을 내보내지 않는다 (2026-09-21)

**검증**: `SavingsStatsApiTest` (`g69_publicSamplesAreRoundedSoNoExactAmountLeaves`)

G-62 로 표본 수를 뺐지만 **개인별 금액 배열은 그대로 나갔다.** `17,958원` 같은 값은 그 사람의
결과를 그대로 공개하는 것이고, 아는 사람이 보면 누구인지 짚을 수 있다.

랜딩이 개별 금액을 돌려 보여 주는 화면이라 **배열 자체를 없앨 수는 없다.** 대신 **1,000원 단위로
뭉갠다** — 같은 칸에 여러 사람이 겹쳐 개인을 못 짚으면서, "이 정도 아꼈다"는 감각은 남는다.

| | 상황 | 정답 |
|---|---|---|
| a | 17,958 · 10,800 · 21,000 | `18000` · `11000` · `21000` |
| b | 평균·중앙값 | **뭉갠 값에서** 낸다 |
| c | 응답 본문 | 원본 금액(`17958`·`10800`)이 **어디에도 없다** |

**b 가 핵심이다.** 원본으로 평균을 내고 표본만 뭉개면 평균에서 원본이 역산될 여지가 남는다 —
**방어를 한 겹만 두면 다른 겹으로 새어 나간다.** G-62 에서 화면에만 방어를 두었다가 API 로 샌
것과 같은 교훈이다.

개수도 30 → **12** 로 줄였다. 랜딩이 그보다 많이 쓰지 않는데 더 주면 노출만 넓어진다.

**화면은 "약"이라고 적어야 한다** — 반올림한 값이다. 프론트에 전달했다.

## G-70. 특가 조회는 못 읽은 것과 끝난 것을 가른다 (2026-09-21, §9 배치 연결)

**검증**: `PlanPromotionOracleTest` (`g70a`~`g70f`)

`mobile_plan_promo` 13행을 **한 번 손으로** 채운 상태였다. **특가는 끝나는 것이 정상**이라
그대로 두면 곧 어긋난다. 매일 09:00 배치가 공식 페이지로 다시 확인한다(AI 계약 §9).

| | 확인 | 정답 |
|---|---|---|
| a | 하나는 읽히고 하나는 못 읽힘 | `promotions` 와 `failures` 로 **갈려서** 온다 |
| b | 출처 URL → 상품 번호 | `/products/7752.do` → `7752`. 형식이 다르면 **빈 값** |
| c | 0개 또는 31개 | 부르지 않는다 — 계약 상한은 1~30 |
| d | 502 | 코드는 `detail.code` 에서 읽는다 |
| e | 숫자 자리에 숫자가 없음 | `CATALOG-SOURCE-CHANGED` — 조용히 넘기지 않는다 |
| f | 쿨다운 안 | 서버에 닿지도 않는다. 대상이 목록이라 **호출 전체를 하나로** 막는다 |

**a 가 이 케이스의 전부다.** 못 읽은 번호를 "특가가 끝났다"로 읽으면 **멀쩡한 특가가 조용히
사라진다.** 그래서 배치는 그 번호의 기존 행을 건드리지 않고, **지우는 제안을 아예 만들지 않는다** —
특가 종료는 사람이 합본에서 행을 빼는 것으로만 일어난다.

**§8 과 다른 점 셋**: ① 한 번에 여러 상품을 물어 **간격은 저쪽이 지킨다**(1.2초, 30개면 36초).
§8 의 읽기 제한 30초를 그대로 쓰면 30개를 못 받는다 — 기본값을 90초로 잡았다.
② 실패가 행 단위다. ③ `regularPrice` 는 **"정가"가 아니다** — "N개월 이후 B원/월" 의 B 이고
13건 중 5건은 지금 금액보다 싸다.

**이름이 어긋나면 제안하지 않는다.** 다른 상품의 값을 우리 행에 넣을 수는 없다 —
`PROMOTION_NAME_DRIFT` 로 운영 타임라인에만 남긴다(§8 의 출처 불일치와 같은 규칙).

## G-71. KB리브모바일 15개 요금제 (2026-09-21, 사용자 지시)

**검증**: `MobilePlanSeedTest` (시드 적재 전체), `CatalogSeedLoaderTest` (행수·시퀀스)

카탈로그에 통신사 21곳이 있었는데 **KB리브모바일이 없었다.** 토스모바일은 있는데 빠져 있었다.

**1차 출처**: `https://m.liivm.com/` · 확인일 2026-09-21. 브랜드 표기는 그 페이지가 스스로 쓰는
`KB리브모바일`(영문 `KB Liiv M`)을 그대로 따랐다. 운영 법인은 푸터의 `KB국민은행`이다.

**`base_price` 는 기본료(할인 전)를 넣었다.** 페이지는 `기본료 → 혜택가` 두 단계로 적는데
(예: `5G 든든무제한 150GB+` 48,900원 → 23,000원), **혜택가의 조건이 페이지에 적혀 있지 않다.**
조건을 못 채운 사용자에게 그 금액을 약속하면 "미사용 혜택은 0원"(절대 원칙 1)을 어기는 셈이라,
확인되지 않은 할인은 넣지 않았다.

**남은 한계**: KB 거래 실적으로 실제 더 싸게 쓰는 사용자에게는 우리 값이 비싸게 잡힌다.
조건부 할인을 담을 칸이 없다 — `promo_months`/`regular_price` 는 **기간**이지 **조건**이 아니다.
조건형 할인을 모델링할지는 별도 결정이 필요하다.

`NGB+` 표기는 소진 후 속도제한 무제한이라 기존 관례대로 무제한 sentinel(999999)로 넣었다 —
`데이터 맘껏 15GB+`·`5G 모두다 맘껏 14GB+` 와 같은 처리다. `1GB`(+ 없음)만 1,024MB 다.

## G-72. 조건형 할인은 알리되 순위에 넣지 않는다 (2026-09-21, 사용자 지시)

**검증**: `RecommendationApiTest#g72_conditionalDiscountIsAnnouncedButNeverRanked`

G-71 이 남긴 한계를 닫는다. KB리브모바일 페이지는 `기본료 → 최종 혜택가` 두 단계로 적는데
(`5G 든든무제한 150GB+` 48,900 → 23,000) **그 조건이 페이지 어디에도 없다.** SKT 망 요금제는
금액 옆에 `최대 할인가(VAT포함)` 라고만 쓴다 — "최대" 는 누구나 그 값은 아니라는 뜻이다.

**기간형과 다른 종류다.** `promo_months`(V32)는 **달력**이라 누구에게나 같고 우리가 안다.
조건형은 **사용자마다 다르고 우리는 모른다.** 같은 칸에 넣을 수 없어 `benefit_price`·`benefit_label`
을 따로 뒀다(V34).

| | 기간형(V32) | 조건형(V34) |
|---|---|---|
| 예 | 7개월 뒤 금액 변동 | KB 실적 충족 시 할인 |
| 누구에게나 같은가 | 예 | **아니오** |
| 우리가 아는가 | 예(달력) | **아니오** |
| 순위에 쓰는가 | **예** | **아니오** |

**두 가지가 동시에 참이어야 한다.** 하나라도 깨지면 사용자가 손해를 본다.
- 순위에 **안 쓴다** — 쓰면 조건을 못 채운 사용자에게 없는 금액을 약속한다(절대 원칙 1과 같은 논리).
- 그래도 **알린다** — 안 알리면 그 요금제는 기본료로 밀려 영영 안 보인다. 숨기는 것도 손해다.

안내는 `missingInputs[field=carrierBenefitCondition]` 로 나간다. 금액과 **출처가 그 금액을 부르는
이름 그대로**(`최대 할인가(VAT포함)`)만 싣고, 조건은 통신사에서 확인하라고 보낸다.
**조건 문구를 지어내면 그 순간 D-43 위반이다** — 테스트 d 가 응답에 "실적"·"카드" 가 없는지 본다.

**남은 것**: 사용자에게 "이 조건을 채울 수 있나요"를 물으면 `benefit_price` 가 순위에 들어올 수
있다. 그건 입력 화면 설계와 묶인 결정이라 발표 후로 미룬다.
