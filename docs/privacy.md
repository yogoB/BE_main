## 수집·이용 동의

- **필수(ESSENTIAL)**: 가입(`AuthService.signup`·`googleLogin`) 시 현재 정책 버전으로 자동 기록. 계약 이행 근거이므로 철회 불가.
- **선택(MARKETING)**: 기본 미동의(행 없음). `POST /api/v1/me/consent/marketing`로 동의/철회. 철회는 `withdrawn_at` 표시.
- `user_consent`는 `(user_id, item)` UNIQUE. 재동의는 버전·시각 갱신.

## 보유기간 자동 파기

`RetentionService`(@Scheduled 기본 매일 한국시간 04:00, `yogobi.retention.cron`으로 조정)가 보유기간 초과분을 파기한다:
- payment_record: paid_at 기준 12개월 초과
- detection_result: detected_at 기준 6개월 초과
- 만료된 auth_email_token·auth_session (로그인 없이도 정리)
- retained_payment_record: 해당 기록의 `retain_until`이 한국시간 오늘 이하일 때만 파기(12개월 분석 기준 미적용)

`purge()`는 유형별 삭제 건수를 반환한다(운영 점검용). 검증: `RetentionServiceTest`(초과분만 파기, 최신 보존).

## 팀원 리뷰 반영: 외부 분석 내역과 법정 보존 증빙의 구분

2026-09-12 사용자 확인: **payment_record는 외부 구독 내역만 저장한다.** `data.md §4`의 Mock·EML·CSV·수기 반입 자료이며 요고비의 주문/매출/세금계산서 원장이 아니다. 따라서 이 테이블 전체에 법정 5년 보존을 자동 적용하지 않는다.

법정 보존 의무가 확인되는 예외 기록은 별도 `retained_payment_record`로 보존한다. 기존 V5의 `payment_record` CASCADE는 분석본에만 유지하며, 보존 사본에는 `app_user`·`payment_record` FK를 두지 않는다. 회원 삭제나 분석본 12개월 파기가 사본을 지우지 않는다. 기존 데이터의 일괄 복사·보존기간 연장은 하지 않았다.

### 확인한 법령과 적용 한계

- 개인정보 보호법 제21조는 불필요한 정보의 파기를 원칙으로 하며 다른 법령의 보존 의무를 예외로 둔다. 예외로 보존하는 정보는 제3항에 따라 다른 정보와 분리 저장·관리한다. 탈퇴가 모든 기록의 무조건 삭제를 뜻하지 않는다. [2026-09-11 시행본](https://www.law.go.kr/LSW/lsInfoP.do?ancNo=21445&ancYd=20260310&efYd=20260911&lsiSeq=283839)
- 전자상거래법 제6조와 **시행령 제6조**에서 대상 거래기록·기간을 정한다. 대금결제/재화 공급과 계약/청약철회 기록은 5년, 불만/분쟁은 3년 등 기록 유형에 따라 다르다. 통신판매중개자는 자신이 처리한 기록 범위가 명시돼 있다. 외부 서비스의 영수증 분석용 사본까지 요고비의 법정 거래 원장이라고 단정하지 않는다. [시행령 제6조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lspttninfSeq=63460)
- 세무 장부·증빙에는 국세기본법 제85조의3 등 별도 규정이 있다. 일반적인 5년 보존도 관련 과세기간의 **법정신고기한**을 기준으로 하므로 `paid_at + 5년`으로 일괄 계산하지 않는다. 적용 기록·기산일·특례를 담당자가 확인해야 한다. [국세기본법 제85조의3](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1026647533)

이는 현재 데이터 흐름에 대한 구현 판단이다. 실제 보존 의무의 존재·범위·필수 증빙 항목은 거래/세무 책임자가 확인한다. 단순 가명화나 회원 ID 삭제만으로 법정 증빙 요건이 충족된다고 판단하지 않는다.

### 분리 보존 사용 조건

`PaymentRetentionService.preserve(paymentId, legalBasis, retentionStart, retainUntil)`은 신뢰한 서버 코드에서만 호출하는 내부 기능이다. 회원이 호출하는 보존 설정/조회 API는 없다.

1. 외부 구독 반입은 기본적으로 호출하지 않는다. 사용자의 `source` 문자열이나 동의 여부로 보존 의무를 추론하지 않는다.
2. 법정 의무가 확인된 경우에만 구체적인 법령 근거·기산일·확정 파기일을 지정한다. 기록을 생성/분류하는 트랜잭션 안에서, 탈퇴나 일반 파기 **전에** 호출한다. 이미 삭제된 기록을 복구하는 기능은 아니다.
3. `retain_until`은 **한국시간 해당 일자부터 파기 가능**한 배타적 종료일이다. 마지막 보존 의무일 다음 날을 넣는다. 코드가 5년을 자동 부여하거나 탈퇴일부터 기간을 다시 계산하지 않는다. 실제 자동 삭제는 그날 이후 첫 스케줄 실행 시 이뤄진다.
4. 입력 오류·존재하지 않는 원본·중복 보존은 실패한다. 기존 증빙과 기한을 덮어쓰거나 줄이지 않는다. 기간 연장/해제 자동화는 구현하지 않았으며 변경 필요 시 별도 근거 확인이 필요하다.
5. 원본을 잠근 동안 보존 사본을 쓰고 같은 트랜잭션에서 커밋한다. 사본 저장 실패를 무시한 채 법정 기록으로 분류를 완료해서는 안 된다.

사본에는 회원 ID·이메일·비밀번호·Google sub·인증 토큰을 복사하지 않는다. 다만 거래 식별자·가맹점 원문·날짜·금액은 다른 자료와 결합해 개인을 식별할 여지가 있으므로 **익명 데이터라고 부르지 않는다.** 사본을 추천·마케팅·AI 입력에 사용하지 않는다.

현재는 같은 DB의 별도 테이블로 논리 분리하고 앱 API 접근을 제공하지 않는다. 실제 법정 보존에 사용하기 전에는 담당자 DB 접근 권한·접근 기록·백업 보존/파기·원본 증빙의 완전성·정보주체 열람 절차도 확정해야 한다. 현재 결제 분석 필드만으로 주문/세금계산서의 모든 필수 증빙을 보존했다고 보고하지 않는다.
