# CSV 카탈로그 운영과 정보 오류 제보

2026-09-15 사용자 지시(D-18). 우체국·스마트초이스 실행 연동은 제거한다.

## 데이터 원본

카탈로그 원본은 버전이 남는 CSV 파일이다. PostgreSQL은 CSV를 반영한 조회용 테이블과 회원 데이터를 저장한다.
CSV 파일 자체를 PostgreSQL 안의 문자열로 중복 보관하지 않는다. 사용자 조회마다 파일을 읽거나 외부 AI를 호출하지 않는다.
추가·수정·삭제는 운영용 도구로 CSV를 바꾸고, 검증된 전체 스냅샷을 DB에 반영하는 순서다.
서비스가 참조 중인 요금제/티어는 물리 삭제 대신 신규 추천에서 제외하며 기존 회원 연결은 보존한다.

## AI 자료의 진입 조건

입력은 이용 조건을 확인한 공식 자료·허락받은 데이터 파일·제공자가 허용한 데이터 접근 방식이다.

**수집 주체는 모델이어도 된다(D-43, 2026-09-17).** 팀원이 자료를 건네주는 방식만 허용하던 것을 바꾼다.
바뀐 것은 **누가 가져오느냐** 하나뿐이고, 무엇을 증거로 인정하느냐는 오히려 더 엄격해진다.

모델이 가져온 값은 아래를 **모두** 갖춰야 후보가 된다. 하나라도 없으면 그 행은 비워 둔다.
1. **1차 출처 URL** — 통신사·서비스 제공자의 공식 페이지, 또는 이용 조건을 확인한 집계처.
2. **원문 인용** — 그 값이 적힌 문장을 그대로 남긴다. **인용문에서 숫자가 직접 읽혀야 한다.**
   인용문을 읽어도 그 값이 안 나오면 근거가 아니다.
3. **확인일** — 문서를 실제로 연 날짜.
4. **이용 조건 근거** — 약관·정책 URL 과 해당 문구. 모델은 이것을 **기록**할 뿐,
   재사용 권한이 있다고 **판정하지 않는다.** 판정은 승인하는 사람이 한다.

검색 결과 요약·모델의 기억·두 모델의 같은 답변은 **여전히 가격의 증거로 인정하지 않는다.**
"가져온다"는 것은 1차 출처 문서를 실제로 열어 그 안의 문자열을 인용한다는 뜻이지,
기억이나 검색 스니펫에서 값을 적어 넣는다는 뜻이 아니다. 이 구분이 D-43 의 전부다.

**요청 중 외부 조회 금지는 그대로다(D-05).** 수집은 오프라인·배치에서만 한다.
사용자 요청을 처리하다가 외부 가격을 읽는 코드는 여전히 만들지 않는다.
로그인/접근 제한 우회나 무단 대량 수집 기능은 만들지 않는다. AI 사용 자체가 재사용 권한을 부여하지 않는다.
robots.txt는 크롤러 트래픽 제어 수단이며, 데이터 재사용 권한을 대신하지 않는다.
근거: [Google의 robots.txt 설명](https://developers.google.com/search/docs/crawling-indexing/robots/intro),
[공공데이터포털 이용 정책](https://www.data.go.kr/ugs/selectPortalPolicyView.do).

검증 순서: 입력 스키마·정수 금액·단위·관계키 → 출처 URL/확인일·이용 조건 확인 → 원자료와 숫자 대조 → CSV 반영.
AI 후보는 검증 전 `ESTIMATED`이고 계산 대상이 아니다. 공식 원자료에 근거해 검수가 완료된 카탈로그만 사용한다.
현재는 **검증 통과 후 운영자 승인**으로 발행한다 — D-43 이후에도 이것은 그대로다.
수집 주체를 넓히면서 검수를 같이 푸는 것은 안전장치를 통째로 없애는 것이다. 승인하는 사람은
위 네 가지(출처 URL·원문 인용·확인일·이용 조건 근거)를 보고 판단한다. 인용문에 숫자가 없으면 반려한다. 아래 도구는 형식·관계·승인 파일을 검사하며 원자료의 진실성이나 이용 권한을 판정하지 않는다.

## 파일 변경과 DB 반영

- 기존 CSV 형식과 COPY/스테이징 검증을 재사용한다. 새 파일은 임시 파일에 쓴 뒤 원자적으로 교체한다.
- 이전 스냅샷 해시를 확인해 동시에 수정한 내용을 덮어쓰지 않는다. 유효하지 않은 입력은 원본을 변경하지 않는다.
- DB는 새 스냅샷 전체 검증이 끝난 뒤 트랜잭션으로 갱신한다. 실패 시 기존 조회 결과를 유지한다.
- 삭제/판매 종료는 명시적인 검토 대상이다. AI 응답에 없다는 이유로 자동 삭제하지 않는다.
- 운영자가 검토한 CSV를 다시 반영할 수 있어야 한다. 카탈로그 수정 권한을 일반 회원에게 열지 않는다.

## “정보가 틀렸나요? 제보해 주세요”

비회원도 공개 결과에서 제보할 수 있다. 대상 상품, 잘못된 항목, 설명, 선택 출처 링크를 입력한다.
이메일·전화번호·결제 원문은 요구하지 않는다. 링크는 근거 문자열로 저장하며 서버가 자동으로 가져오지 않는다.
접수는 원본 가격을 바꾸지 않는다. 운영자가 원자료를 확인하고 CSV 수정 도구를 통해 반영한다.
공개 조회는 제공하지 않으며 접수 번호와 완료 안내만 반환한다. CSRF·요청 빈도·본문 길이를 제한한다.

신규 기능의 구체 계약은 `docs/BE_API.md`에 기록한다. 계산 엔진과 추천 순위 기준은 유지한다.
현재 BE 내장 검증 화면의 요금제·추천·계산 결과 카드에 연결했다. 별도 서비스 프론트에서는 같은 API를 연결한다.
서비스·구독 티어·번들 제보도 API가 지원한다. 제보는 90일 경과 후 첫 정기 파기 실행에서 삭제한다.

## 팀원 실행 순서

Python 3.9 이상(macOS/Linux)의 표준 라이브러리만 사용한다. 저장소는 신뢰한 운영자만 쓰기 가능하게 하고,
서버는 같은 디렉터리를 읽을 수 있어야 한다. 저장소·검수 기록은 백업하고 공개 정적 파일 경로에 두지 않는다.
파일 잠금은 한 호스트에서만 사용한다. 여러 서버가 동시에 파일을 발행하는 구성은 지원하지 않는다.

```bash
# 레포 루트에서 실행. 작업 폴더는 매번 새로운 경로를 쓴다.
python3 scripts/catalog_csv.py init --input-dir /tmp/yogobi-catalog-edit --store /srv/yogobi/catalog
# 작업 폴더의 CSV를 수정한 다음 검수 초안을 만든다.
python3 scripts/catalog_csv.py prepare --input-dir /tmp/yogobi-catalog-edit --store /srv/yogobi/catalog > /tmp/yogobi-catalog-review.json
```

첫 `init`은 보유 시드(서비스 6·티어 17·번들 **7**, 요금제 **1,706**)를 복사한다. 제휴 혜택 CSV는 아직 없어 헤더만 생성된다.
`*_TEMPLATE.csv`와 `db/dev/` 가상 요금제를 운영 자료로 복사하지 않는다.

### 수집 매트릭스를 CSV로 옮길 때

팀이 공식 사이트에서 확인해 만든 매트릭스(35열)는 `scripts/catalog_matrix_to_csv.py`로 변환한다.

```bash
python3 scripts/catalog_matrix_to_csv.py <매트릭스.csv> <작업폴더>/mobile_plan.csv --include-conditional
```

- **값을 지어내지 않는다.** 망을 단정할 수 없거나(미표기·태블릿) 월정액·데이터량이 비면 그 행을 빼고 **사유별 개수를 출력**한다.
- 통화·문자가 `기본제공`처럼 수량 없는 표기면 **빈칸(미확인)**으로 둔다. `0`은 "미제공"일 때만 쓴다(V11에서 NULL 허용).
- `5G/LTE` 통합 상품은 `5G`로 넣는다. 스키마가 망 하나만 담는 데서 오는 알려진 한계다.
- 출처 URL의 query·fragment는 발행 규칙에 맞춰 떼어낸다. 상품 식별값(공식상품ID)은 검수 사유에 남긴다.
- 같은 `(통신사, 요금제명)`이 여럿이면 중복대표 → 공식확인 → 추천 가능 → 확인일 최신 순으로 **1건만** 남긴다.
- 규칙 검사: `python3 scripts/test_catalog_matrix_to_csv.py`

제휴 혜택도 같은 매트릭스에서 뽑는다:

```bash
python3 scripts/catalog_benefits_from_matrix.py <매트릭스.csv> <작업폴더>/plan_benefit.csv
```

요금제명의 공식 표기만 근거로 쓴다. **등급이 표기된 행만 `FREE`로 계산에 넣고**, 서비스만 적힌 행은
`BUNDLE_INCLUDED`(금액 효과 0, 표시만)로 둔다 — 등급을 모른 채 `FREE`로 넣으면 프리미엄 등급까지
0원이 되어 실제보다 싸게 추천한다. **스마트초이스는 쓰지 않는다**(저작권 정책상 단체의 복제 불허, `data.md §1-C`).

SKT는 상품 상세의 구독 혜택 표에서 등급·할인액을 확정할 수 있다. 먼저 수집한 뒤 `--details`로 넘긴다:

```bash
python3 scripts/fetch_skt_ott_benefits.py <매트릭스.csv> /tmp/skt_ott.json
python3 scripts/catalog_benefits_from_matrix.py <매트릭스.csv> <작업폴더>/plan_benefit.csv --details /tmp/skt_ott.json
```

수집은 **1회 오프라인**이며 요청 간 1.2초를 둔다. 서비스는 발행된 CSV만 읽는다(런타임 호출 금지, D-05).
등급을 사용자가 고르는 상품(베스트 Max·Pro)과 묶음 상품(티빙&웨이브)은 확정하지 않고 `BUNDLE_INCLUDED`로 남긴다.
이후 `init`은 현재 발행본을 복사하므로 일부 상품을 수정할 때도 **5종 전체 파일**을 유지한다.

1. 기존 ID는 유지한다. 새 서비스·티어·번들은 미사용 양의 정수 ID를 부여한다. 요금제는 `(carrier, plan_name)`이 식별 기준이다.
2. 원자료와 기본료·할인 기간·데이터 단위·서비스 등급·택1 조건을 대조한다. 숫자를 모르면 추측해 넣지 않는다.
3. 검수 JSON의 `expected_revision`·`files` 해시는 그대로 두고 `approved_by`, `reason`, `sources`를 채운다.
   모든 변경 행의 자료와 재사용 근거를 사람이 확인한다. URL 목록과 각 행의 대응은 자동 검증하지 않는다.
4. CSV를 다시 바꿨다면 `prepare`부터 다시 한다. 해시가 달라지면 기존 승인은 거부된다.

검수 JSON에서 직접 채우는 부분의 예시(예시 값을 그대로 승인에 쓰지 않는다):

```json
{
  "approved_by": "검수 담당자",
  "reason": "공식 월요금 변경과 판매 종료 확인",
  "sources": [{
    "url": "https://provider.example/pricing",
    "usage_basis": "확인한 데이터 제공 약관 조항 또는 제공자의 사용 허락 기록",
    "checked_at": "2026-09-15"
  }]
}
```

출처는 인증정보·query·fragment 없는 HTTPS 주소다. 필요한 상품 식별 정보는 검수 사유에도 남긴다.
현재 검증은 파일당 10MB·10,000행, 필드 2,000자, 정수 금액·연간 합계 범위, 관계키·혜택 형식 등을 검사한다.

```bash
python3 scripts/catalog_csv.py publish --input-dir /tmp/yogobi-catalog-edit --store /srv/yogobi/catalog --review /tmp/yogobi-catalog-review.json
# 삭제 또는 혜택 행 교체가 있으면 검토한 뒤 위 명령에 --allow-deletions 추가
```

서버 `.env`에 `CATALOG_CSV_DIR=/srv/yogobi/catalog`를 설정하고 재시작한다. 이 값이 설정되면 내장 시드 덮어쓰기는 건너뛴다.
새 CSV는 `revisions/<해시>/`에 보존되고 `current` 파일이 발행본을 가리킨다. 서버는 시작 시와 기본 60초마다 변경을 확인한다.
로그의 `CSV 카탈로그 반영 완료: <해시>`와 `/api/v1/catalog/services`, `/api/v1/catalog/plans` 조회로 반영을 확인한다.
발행과 DB 갱신은 서로 다른 단계다. 발행 직후에는 최대 한 주기 동안 이전 DB가 보일 수 있고, DB 반영 실패 시에는
**이전 DB를 유지한 채 재시도**한다. 파일 발행까지 함께 롤백되는 분산 트랜잭션은 아니다.

CSV에서 뺀 상품은 `active=false`로 신규 조회·추천·선택에서 제외한다. 기존 회원 참조와 ID는 보존하며 재추가하면 활성화한다.
기존 서비스·티어 ID를 다른 상품에 재사용하지 않는다. 요금제 이름을 변경하면 새 자연키이므로 기존 상품 판매 종료와 신규 추가로 취급한다.

### 오류와 복구

- 승인/해시/입력 오류: `current`는 그대로다. 원자료와 CSV를 고치고 `prepare`부터 다시 실행한다.
- 동시 발행 충돌: 현재 버전으로 새 작업 사본을 만들고 변경을 다시 반영한다. `expected_revision`만 억지로 고치지 않는다.
- DB 반영 실패: 서버 DB 연결·제약 오류를 조사하고 수정본을 재검수·발행한다. 기존 DB를 비우지 않는다.
- 이전 자료로 복구: 새 `init` 폴더에 `revisions/<복구할 해시>/`의 CSV 5개를 복사한 뒤, **현재 버전 기준**으로
  `prepare`→복구 사유·재검수→`publish`한다. 제거가 있으면 `--allow-deletions`가 필요하다. 발행본 파일을 직접 고치지 않는다.

## 운영자 제보 처리

운영 DB에서 `catalog_report`의 `PENDING` 행을 확인한다. 전용 관리자 화면·제보 공개 조회 API는 없다.
개인정보가 잘못 적혔다면 본문을 처리에 필요한 내용으로 줄이거나 삭제한다. 출처 링크를 신뢰해 자동 실행하지 않는다.
원자료 확인 → CSV 수정·검수·발행 → DB 반영 확인 후 해당 UUID 행의 `status`를 `RESOLVED`로 바꾼다.
근거가 없거나 잘못된 제보는 `REJECTED`로 처리한다. 접수했다고 가격이 자동 변경되거나 사용자에게 별도 알림이 발송되지는 않는다.
`catalog_candidate`(V10)는 “상품이 없다”는 결손 수집 우선순위이며, “기존 정보가 틀렸다”는 이 제보와 구분한다.

## 성공 기준

1. 실행 코드·설정에 우체국·스마트초이스 호출/스케줄 의존이 없다.
2. CSV의 무효 금액·출처 누락·관계 불일치·동시 수정은 원본과 기존 DB를 훼손하지 않는다.
3. 승인 자료의 추가·수정·추천 제외가 CSV와 API 조회에 반영된다.
4. 제보 접수는 대상 검증·CSRF·길이/빈도 제한을 통과해야 하며 카탈로그를 직접 수정하지 않는다.
5. 기존 추천/계산/회원/인증 골든·통합 테스트가 통과한다.
